# carlos-podman — fifteenth-pass review + live end-to-end test report (2026-08-02)

Scope: a fresh review of `carlos_ctl/`, the Containerfiles and the Ansible
role, **plus a full live end-to-end exercise** in a rootless-podman sandbox
(podman 4.9.3, Ubuntu 24.04, **no systemd PID 1**, cgroup **v1**,
TLS-intercepting egress proxy that serves CONNECT only, `nofile` hard cap
4096): real image builds from source, `podman kube play` of the dev spec
against `carlos-emr/carlos@af909f50` + `drugref2026@101063bb`, the Ontario
Flyway schema (427 tables), the app repo's Playwright login suite (twice), a
destructive point-in-time restore, and a systematic drive of the **complete**
`carlos-ctl` verb matrix — every verb in `cli.py`'s dispatch. Everything
reported fixed through `REVIEW-2026-08-02-pass14.md` was treated as baseline;
only NEW findings are reported here.

The pods ran **rootless as the `carlos` service user** (the production
topology), so every `runuser` / `XDG_RUNTIME_DIR` / subuid boundary in
`carlos_ctl.runner` was exercised for real rather than as root.

## New findings

### H1 (HIGH, deploy-blocking): a too-narrow pre-existing subuid/subgid grant is never checked, and every downstream failure blames something else

**Hit live, and it cost a 40-minute build.** The service user's rootless
userns must map every container id this deployment pins. The ceiling is
**65534**: the mysqld-exporter runs as that uid, and — less obviously —
`apt-get` drops to `_apt`/`nogroup` **inside the image builds**.

The Ansible role allocates a 65536-wide range, but only when the user has no
grant at all:

```yaml
if grep -q "^{{ carlos_service_user }}:" /etc/subuid 2>/dev/null; then
    exit 0
fi
```

A service user that arrives with a *narrower* grant — a pre-existing
account, a site allocation, a hand-edited `/etc/subuid` — keeps it, and
**nothing anywhere checks the width**: not the grant task, not `asserts.yml`,
not `carlos-ctl`. Worse, rootless podman 4.9 builds its map from the **first**
grant only, so the intuitive repair (append another range) does not widen it
— measured here: grants `carlos:165536:34464` + `carlos:200000:65536`
produced exactly

```
$ podman unshare cat /proc/self/uid_map
         0       1001          1
         1     165536      34464
```

Every consequence points the operator somewhere else:

- **Image builds die in the runtime stage**, tens of minutes in, on
  `E: setgroups 65534 failed - setgroups (22: Invalid argument)` from apt —
  which reads like a broken base image, not a host misconfiguration.
  (Observed live: the first `carlos-ctl build` of this pass failed here
  after the full Maven compile.)
- **`podman unshare chown 65534:65534 exporter.my.cnf` fails `EINVAL`**, so
  an obs-enabled install silently loses all MariaDB metrics. This is the
  *same symptom* pass-14 H1 fixed for a different cause (`EPERM` from an
  unmapped host root), and play's warning still sends the operator to check
  the file's `owner:group` and that "the subuid/subgid ranges in
  /etc/subuid, /etc/subgid" exist — which they do, just too narrow.
- **Below 10014 the app pod cannot start at all** (`carlos-init` chowns to
  10001, caddy to 10013).

Fixed in three places:

- `carlos_ctl/validate.py`: new `subid_map_preflight()` reads the FIRST
  grant for the service user out of `/etc/subuid` and `/etc/subgid` and warns
  when it cannot cover container id 65534, naming the ceiling, the `EINVAL`
  mechanism, and — explicitly — that the fix is to **widen** the existing
  grant, not append a second one. Absent/unreadable grants stay silent
  (podman fails loudly on those by itself).
- Wired into `validate_instance()` (so **`play`** warns before the exporter
  chown fails) and into **`cmd_build`** next to the `nofile` floor check, so
  a doomed build says so at second 1 instead of minute 40.
- `ansible/roles/carlos_podman/tasks/host.yml`: a hard `assert` immediately
  after the grant task — the role owns the allocation, so provisioning is
  where this must refuse rather than warn. It re-slurps both files (the
  grant task may have just written them) and fails with the `usermod
  --del-…/--add-…` + `podman system migrate` remedy.

Warn (not refuse) on the CLI side is deliberate: the measurement comes from
host files `carlos-ctl` does not own, and an emergency `play` must never be
blocked by a best-effort probe. The playbook is the hard gate.

Pinned by: 6 unit tests (`TestSubidMapPreflight` — including that an
*appended* second range does not satisfy the check, the 65534 off-by-one, and
that `xcarlos` is not read as `carlos`), 3 hermetic e2e assertions driving
`build` against fixture `/etc` dirs, and 1 static `ansible-checks.sh` pin.
Documented in QUICKSTART step 0 (with the widen recipe), both troubleshooting
tables, and the README's "no MariaDB metrics" row (which previously described
only the `EPERM` half of the failure).

### H2 (HIGH, host damage from the test suite): `pytest tests/unit` run as root silently decommissions a live `carlos` instance

`tests/unit/conftest.py` already carried an autouse fixture whose docstring
says why — "a ROOT pytest run (CI runs the suites under sudo) writes … into
the host's REAL /run — the leak the pass-8 review measured live". It
redirected exactly one knob (`CARLOS_RUN_DIR`). `Settings` resolves **six
more** host paths, each with a `CARLOS_*_DIR` override that config.py
documents as existing "ONLY so the hermetic test suite can run without
touching the host" — and none of them was being set. Meanwhile `cmd_uninstall`
acts on those paths for whatever `INSTANCE` the Settings under test carries,
which is `carlos`: the same default name a real deployment uses.

Measured live on this host, with canaries planted and one
`pytest tests/unit` run as root:

| canary | before | after |
| --- | --- | --- |
| `/etc/systemd/system/carlos-backup.timer` | present | **DELETED** |
| `/etc/systemd/system/carlos-monitor.service` | present | **DELETED** |
| `/etc/systemd/system/carlos-secrets.service.d/credentials.conf` | present | **DELETED** |
| `/etc/tmpfiles.d/carlos-emr.conf` | present | **DELETED** |
| `/run/carlos-emr/carlos-db.properties` | present | **DELETED** |
| `/etc/carlos-podman/instances/carlos.conf` | present | **DELETED** |
| `/etc/carlos-podman/instances/carlos.alert.env` | present | **DELETED** |

…while the suite reported **"528 passed"**. Data is untouched, but that is a
silent decommission of a PHI instance's backup schedule, its monitoring
timer, its `/run` sealed-credential fragments (the app fails its `__SEALED__`
guard at the next restart), its `/run` tmpfs persistence, its registry claim
— which also makes the role's cross-instance collision asserts stop seeing
it — and the alert-channel mirror that exists precisely so guard pages stay
deliverable when `$EMR_HOME` is unmounted.

The **read** direction was broken too: `Settings` falls back to
`<registry>/<instance>.alert.env` for `ALERT_WEBHOOK`/`ALERT_EMAIL`/
`HEARTBEAT_URL`, so with a real mirror present **9 tests failed** — suite
results depended on the machine they ran on.

This is reachable in practice: the documented dev loop is a checkout on a
workstation, `make test` runs `pytest tests/unit`, and the conftest's own
comment establishes that CI runs it under sudo. A developer VM (or an EMR
host used for a quick `make check`) that also runs an instance named
`carlos` loses the above.

Fixed by extending the fixture to every knob (`_HERMETIC_DIR_KNOBS`), and by
passing the redirects through `mk_settings` as well — `Settings` reads them
from the mapping it is handed, not from `os.environ`, so `monkeypatch.setenv`
alone left every constructed Settings pointed at `/etc`. One consequence had
to be handled explicitly: `CARLOS_SYSTEMD_DIR` doubles as the "I am the
hermetic harness, do not touch the kernel ruleset" marker for the three
root-only nft probes, so a new `live_host_probe` fixture lets the three
`TestHostfwCheck` tests opt back out — with a comment naming the overloading,
since that coupling is a trap for the next test author.

Pinned by `test_every_host_path_setting_is_redirected` in `test_config.py`
(deliberately in a collected module — pytest does not collect tests from
`conftest.py`), which asserts every host-path Settings attribute lands inside
the test's `tmp_path`. Verified to bite: removing one knob from the fixture
makes it fail naming `instance_registry_dir=/etc/carlos-podman/instances`.
After the fix the same canary run is **529 passed with all seven canaries
intact**.

## Not findings (checked, behaved correctly)

- **`db-backup` argument contract** (pass-14 H2): `--help`, two positional
  arguments, a `!`-bearing name and an existing target directory are all
  refused *before* the credential lookup and the snapshot.
- **The Rourke PITR exception** (pass-13): on a fresh ON install the engine
  audit finds exactly `oscar.formRourke2009 [Aria]`, prints it as
  KNOWN-unconvertible, and proceeds with a loud accepted-gap warning instead
  of refusing every fresh install.
- **Runtime binlog-latch detection** (pass-13): `check` reported
  `binary logging is OPEN at runtime (SHOW BINLOG STATUS)`, i.e. the probe
  that `@@log_bin` cannot make.
- **`pma --ttl` exit code** (pass-12): a session ended by its TTL exits 0
  with the explanatory line, not `timeout`'s 124.
- **Credential drop-files**: a generated root/restic password on a
  non-terminal run is written 0600 to `secrets-private/.new-*` and named in
  the log, never echoed into the journal. (An earlier suspicion that the
  file vanished immediately was my own `ls` without `-a`.)
- **Setup wizard YAML quoting**: the default Ontario answer renders
  `carlos_billing_province: "ON"` — a string, not YAML-1.1 `true` — and the
  db password is `!vault`-encrypted when a vault password source is given,
  refused in plaintext when it is not.
- **Seal fail-loud**: with no systemd bus, `seal` completed every durable
  mutation and then failed rc 1 on `daemon-reload` with the "the seal itself
  is complete; re-run (idempotent)" message, rather than reporting success
  over a render unit that would never start.
- **`db-users` atomicity pre-check**: with `drugref2.properties` missing it
  refuses *before* the SQL runs, instead of stranding a half-rotated state.

## Environment notes (not defects in this repo)

- The sandbox's egress proxy serves **CONNECT only** and answers `405` to
  plain-HTTP proxying, so `apt-get` inside the image builds needed a local
  HTTP→HTTPS upgrading forward proxy in front of it. Nothing in this repo is
  involved; the Containerfiles fetch through whatever `HTTP(S)_PROXY` the
  build inherits.
- No systemd PID 1: every `systemctl` path (unit install, timer arming,
  `--user -M`) legitimately fails here. Those failures are reported as such
  in the matrix above, not as findings — each one is the code's documented
  loud-failure branch.
- cgroup v1: rootless resource limits are silently unenforced, which is why
  the dev pod spec omits them (documented in its header).
