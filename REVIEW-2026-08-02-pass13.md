## New findings

### H1 (HIGH, backup/PITR). Binary logging can stop at runtime with `@@log_bin` still reading 1 — the 15-minute ship then reported success forever over a frozen chain. **Fixed.**

**What happened.** MariaDB latches binary logging **off for the rest of the
server process** the first time it cannot open a new binlog file. Reproduced
live, twice, on the pinned `mariadb:11.4.12`:

```
2026-08-02 16:14:06 13 [ERROR] Could not use /var/lib/mysql-binlog/binlog.000006
for logging (error 13). Turning logging off for the whole duration of the
MariaDB server process. To turn it on again: fix the cause, shutdown the
MariaDB server and restart it.
```

`error 13` is `EACCES`; `ENOSPC` on a full binlog volume does the same. Both
are ordinary failure modes for a dedicated `data/mariadb-binlog` mount, and
this deployment gives that mount its own volume precisely so it *can* fill
independently.

**Why nothing noticed.** `BackupContext` derived its only binlog-health signal
from `SELECT @@log_bin` — which reports the **startup option** and keeps
reading `1` after the latch. Measured live in the latched-off state:

| Probe | Answer |
|---|---|
| `SELECT @@log_bin` | `1` (i.e. "healthy") |
| `SELECT @@gtid_binlog_pos` | `0-1-1834` (stale, but non-empty) |
| `SHOW BINLOG STATUS` | **empty result set** — the binlog is CLOSED |
| `SHOW BINARY LOGS` | `ERROR 1381 (HY000): You are not using binary logging` |

So every guard in `backup.py` believed PITR was healthy. The observed
behaviour of each consumer, measured through the CLI's own code path:

| Path | Cadence | Pre-fix behaviour with PITR dead |
|---|---|---|
| `backup binlogs` | every 15 min | **rc 0, "Backup (binlogs) complete", stamps `.last-binlog-ok`** |
| `monitor` binlog freshness | every 15 min | **green** — the stamp is fresh |
| `carlos-ctl check` | on demand | **zero** binlog checks |
| `backup full` | nightly | rc 1, but blaming *"db down or credentials wrong?"* |

The ship kept succeeding because the two things it checks both pass in the
latched-off state: `FLUSH BINARY LOGS` becomes a **no-op that returns 0** once
logging is off, and the already-closed binlogs are all still on disk to
re-ship (restic dedups them, so even the snapshot size looks normal). The only
signal was the nightly full failing — up to 24 hours later — with a diagnosis
that sends the operator to check the pod and the credentials, both of which
are fine. The real cause is one line above in the same output
(`Couldn't execute 'SELECT BINLOG_GTID_POS(...)': You are not using binary
logging (1381)`) and in the db container log, which nothing points at.

Net exposure: **point-in-time recovery silently dead for up to a day**, with
the 15-minute job actively reporting success the whole time, on the system
whose entire advertised RPO is "one binlog interval, not one day".

**Fix.** A runtime-authoritative probe, `BackupContext.binlog_runtime_open()`,
using `SHOW BINLOG STATUS` (one row = open, zero rows = closed) with the
pre-11.4 `SHOW MASTER STATUS` spelling as fallback. It needs only
`BINLOG MONITOR`, which is MariaDB's alias for the `REPLICATION CLIENT` the
least-privilege `backup` account already holds — verified live: the probe
answers correctly running as `backup`, not just as root. Three consumers:

- `ship_binlogs` **refuses before the FLUSH** and does not stamp
  `.last-binlog-ok`, so the monitor's `BINLOG_MAX_AGE_MIN` check pages within
  ~35 minutes instead of never.
- `_full_backup` **refuses before running the dump** (rather than burning a
  multi-GB dump to reach a failure) and names the real cause and remedy.
- `carlos-ctl check` gained a FAIL for it — `check` is what an operator runs
  when something feels wrong, and it must be able to say this.

`None` (probe unanswerable) is deliberately **not** treated as closed: an
unknown answer leaves the pre-existing guards in charge rather than turning a
credential blip into a missed nightly backup.

Verified live, both directions, on the running pod:

```
latched off →  backup binlogs   rc 1, no .last-binlog-ok, no FLUSH issued
               backup full      rc 1, refused BEFORE the dump
               check            FAIL binary logging is CLOSED at runtime ...
               monitor          FAIL binlog backup has NO success stamp
repaired    →  backup binlogs   rc 0, stamp written
               backup full      rc 0, retention + prune + check --read-data
               check            ok   binary logging is OPEN at runtime ...
```

Tests: 9 unit pins (both spellings, the empty-result-means-closed case, the
unknown-is-not-closed case, both refusals, and that neither mutates before
bailing) and 7 e2e pins behind two new stub knobs (`STUB_BINLOG_CLOSED`,
`STUB_BINLOG_STATUS_UNSUPPORTED`). Mutation-checked: disabling the guard fails
3 unit tests and 3 e2e cases.

README: a new "Binary logging can stop without stopping the server" subsection
under the binlog-shipping tier, stating the failure mode, why `@@log_bin`
cannot see it, what each verb now does, and the recovery (fix the volume,
**restart the db container** — nothing less re-opens the log — then take a
fresh `backup full` to re-anchor the chain).

**Related check, clean:** `@@server_uuid` (fixed in pass 11) and `@@log_bin`
were the only two places in the tree that read a server variable as if it were
runtime state; there is no third instance of this class.

## Things that were checked and found correct

Recorded so a future pass need not re-derive them:

- **The mutating lock is real.** A `db-backup` fired while a genuine
  `carlos-ctl build` held `/home/carlos/emr/.carlos-ctl.lock` failed fast with
  the documented message; `status` and `backup status` were unaffected.
- **`rotate db`'s re-seal preflight fires BEFORE the mutation.** On a sealed
  install without a TPM it refused up front, naming the exact consequence
  ("the post-rotation re-seal would refuse AFTER the passwords were already
  changed"). Nothing was changed.
- **`rollback`'s schema gate works in both directions**, proven by altering
  the live `oscar` schema between builds rather than by faking a fingerprint.
- **The PITR chain-identity defense is live** end to end: a lineage id was
  minted into the datadir on first backup, rode the dump header and the binlog
  snapshot sidecar, and was re-anchored by the completed restore.
- **`.extra-ca-bundle.crt` is restored on the failure path too.** The first
  build attempt died mid-flight (sandbox networking); the placeholder came
  back to 0 bytes and `git status` stayed clean.
- **Every refusal message names its override.** Across ~40 refusals driven in
  this pass, each printed the specific env knob or flag that accepts the risk;
  none required reading the source to work out how to proceed.
- **`check` is honest on a dev topology** (9 passed / 10 failed at the end):
  it does not soften missing WAF/obs/networks into warnings.

## Environment notes (not product findings)

- **No systemd PID 1.** `enable`, `seal`'s unit install, `down --disable` and
  the `instances` STATUS column all degrade — and every one of them said so
  loudly and accurately rather than reporting success. `seal` in particular
  wrote the bundle, then failed on `daemon-reload` with "The seal itself is
  complete; fix the unit and re-run (idempotent)" — the right split.
- **podman healthchecks need systemd timers**, so container health stayed
  `starting` forever here. Readiness was confirmed by probing the app
  directly. This is why `carlos-ctl play`'s readiness gate could not be
  exercised end to end in this sandbox.
- **Rootless networking needed `/dev/net/tun` to be openable** by the service
  user before `slirp4netns` would come up; the first build failed on it. Not
  a repo issue — a sandbox capability.
- **Two setup gaps were mine, not the code's**, and both are handled by the
  Ansible role's ownership sweep (`_sweep_dirs` in `instance.yml`):
  `conf/restic` and `conf/drugref` must be service-user-owned for the rootless
  restic container to read them. A hand-built instance that skips the sweep
  gets a `permission denied` from restic naming the exact file.
