# carlos-podman — twenty-first-pass review + live end-to-end test report (2026-08-04)

Scope: a fresh review of `carlos_ctl/`, the Ansible role, the Containerfiles
and the four gate suites, plus a **live end-to-end deploy of the full
production topology on a bare host** — `carlos-ctl setup` → `ansible/site.yml`
→ both images built from source with `carlos-ctl build` → all three pods
started → the Ontario Flyway schema and the DrugRef database loaded through
`carlos-ctl db` → `carlos-ctl check` → the app repo's Playwright suites
through the WAF → the backup tiers → a systematic drive of the `carlos-ctl`
verb matrix. Everything reported fixed through
`REVIEW-2026-08-03-pass20.md` was treated as baseline; only NEW findings are
reported here.

Environment: podman **4.9.3** (the documented floor), Ubuntu 24.04, cgroup v1,
native overlay storage, TLS-intercepting egress proxy, **systemd installed but
NOT running as PID 1** — `/usr/bin/systemctl` is present and every call to it
exits nonzero. That third host shape is what this pass adds: pass 19 shimmed
`systemctl` so the deploy exercised the primary (systemd) branch, pass 20
removed the binary entirely so it exercised the documented no-systemd
fallback. Neither had exercised the shape where the binary is **present and
useless**, which is what a container image, a WSL distribution or a chroot
actually looks like — and which is what H3 below is about.

## New findings

### H1 (HIGH): CI has not run the hermetic e2e suite since 2026-08-03 — a shellcheck warning fails the gate step before it, and the suite step is silently `skipped`

`.github/workflows/tests.yml`'s `e2e` job runs four steps in order: bash
syntax, `shellcheck -S warning …` (enforcing), the CLI's python deps, and
then `sudo tests/run-tests.sh`. Since `f1e918a` (pass 18) `tests/ansible-checks.sh`
has carried

```bash
case "$svc_home_default" in
    *'/run/'*|*'/var/run/'*)
```

which shellcheck flags **as a warning** — SC2221/SC2222, because
`/var/run/carlos` contains the substring `/run/` and is already matched by the
first alternative, making the second dead. `-S warning` makes that fatal, so
the job stops at step 2 and GitHub marks the remaining steps `skipped`:

```
shellcheck (enforcing)          failure
python deps for the CLI …       skipped
hermetic e2e suite              skipped     ← never ran
```

Verified against the live run history: every `tests` run since
2026-08-03T15:58 is red, `e2e` is the only failing job, and the failure is
this warning — confirmed in the job logs of the newest `main` run
(`e9b4dff`, run 30861433876) and of the pass-20 branch head (`985f4b7`, run
30858598886). Three `main`-branch runs are affected, and every branch push
in between.

The consequence is not "CI is red" — it is that the suite carrying the
**regression coverage for essentially every finding of passes 1–20** (341
assertions) has not executed in CI for the whole of the pass 18-20 work,
including the commits that added new cases to it. The three findings below
are all things that suite would have been asked to catch.

**Fix.** Drop the dead alternative (one pattern, same semantics — both
spellings still fail the check) and say in a comment why the pair cannot come
back. `shellcheck -S warning tests/run-tests.sh tests/ansible-checks.sh
tests/stubs/*` is clean locally against shellcheck 0.9.0, and the e2e suite
then runs.

**Confirmed in CI.** On this branch's own push (`e83d604`, run 30869652609)
the `e2e` job is **green**: `shellcheck (enforcing)` success, then
`hermetic e2e suite` **success** in 4m06s — the first execution of that step
since pass 18, on a runner that *does* have systemd, which is also the
positive proof for H2 below.

### H2 (HIGH): the suite's "host with no systemd" model leaked the host's REAL `/usr/bin/systemctl`, so the seven assertions pinning pass-20's H2/M1/M2 fixes fail on any systemd host — and a root run reaches the live system manager

`tests/run-tests.sh` models a systemd-less host by building a stub directory
that omits the `systemctl` stub — and then appending the host's own bin dirs:

```bash
for _s in "$ROOT"/tests/stubs/*; do
    [ "$(basename "$_s")" = systemctl ] || ln -sf "$_s" "$NOSD_PATH/"
done
…
env PATH="$NOSD_PATH:/usr/bin:/bin" … python3 -m carlos_ctl.cli seal
```

`/usr/bin/systemctl` exists on every production target, on developer laptops,
and on the `ubuntu-latest` CI runner, so inside the very tests that exist to
prove the no-systemd fallbacks, `shutil.which("systemctl")` found it and
`Runner.have("systemctl")` returned **True**. Measured here:

```
resolved systemctl under the model PATH: /usr/bin/systemctl
shutil.which('systemctl') inside the model -> /usr/bin/systemctl
```

and the suite reported **332 passed, 7 failed** — the failures being exactly
the pass-20 regression cases:

```
FAIL no-systemd seal renders the credential fragments INLINE
FAIL the inline-rendered fragment carries the real password
FAIL no-systemd seal names the standing boot requirement
FAIL no-systemd play warns that NO schedule is armed
FAIL the warning names the jobs that will never run
FAIL it still returns True (the fallback deploy is a documented mode)
FAIL no-systemd rotate obs restarts the obs pod via kube play
```

So the pass-20 fallbacks had **no working regression coverage anywhere except
a systemd-less sandbox** — and H1 above is why nobody saw the red.

There is a containment half too. The suite documents itself as hermetic ("no
root, no podman, no systemd … nothing outside that directory is touched") and
CI runs it **under sudo**. Taking the systemd branch means `seal` issues
`systemctl daemon-reload`, `systemctl enable <instance>-secrets.service` and
`systemctl restart <instance>-secrets.service` against the host's real system
manager. `CARLOS_SYSTEMD_DIR` redirects where the unit FILE is written, not
where `systemctl` looks — so on a host that also has a real instance
provisioned (the obvious machine to run the suite on), those calls resolve
`/etc/systemd/system/carlos-secrets.service` and restart the live instance's
secrets unit with the test's fabricated state. Same class as the pass-15 H2
and pass-17 H8 containment leaks, one mechanism over.

**Fix.** Build a sanitized system-bin directory (symlinks to every
`/usr/bin`, `/bin`, `/usr/sbin`, `/sbin` entry **except** `systemctl`) and
point the model PATH at stubs + that, with no raw host bin dir anywhere. Two
new static assertions gate the model itself before the first case runs — that
the model PATH resolves **no** `systemctl`, and that it still resolves the
other stubs — so a future edit that re-admits a systemctl-bearing directory
fails where the cause is named rather than silently testing the wrong branch.
Suite: 332/7 → **341 passed, 0 failed**.

### H3 (HIGH): `have("systemctl")` is not "systemd works" — on a host where the binary is present but systemd never booted, every no-systemd fallback fails to engage, and `seal` shreds the plaintext and leaves the EMR unable to start

Nineteen decision sites asked `runner.have("systemctl")` and treated the
answer as "this host has systemd". It does not: Debian/Ubuntu ship
`/usr/bin/systemctl` inside container images, WSL distributions and chroots
where systemd is not PID 1, and there **every** call exits nonzero with
`System has not been booted with systemd as init system (PID 1). Can't
operate.` This sandbox is exactly that host, which is how the class surfaced.

Measured live on this host, on the deployed instance, with the pre-fix CLI —
`carlos-ctl play` after the schema load:

```
WARNING: could not start carlos-backup.timer — start it by hand: systemctl start carlos-backup.timer
WARNING: could not start carlos-binlog.timer — start it by hand: systemctl start carlos-binlog.timer
WARNING: could not start carlos-docs.timer — start it by hand: systemctl start carlos-docs.timer
WARNING: could not start carlos-backup-verify.timer — start it by hand: systemctl start carlos-backup-verify.timer
WARNING: could not start carlos-monitor.timer — start it by hand: systemctl start carlos-monitor.timer
WARNING: the stack is up but one or more scheduled timers is missing or failed to start … fix the schedule before treating this deploy as complete
# echo $?
1
```

A fully serving stack — front door 200 through the WAF, 427-table Ontario
schema, DrugRef answering — that `play` can **never** report green on, with
remediation advice (`systemctl start …` by hand) that cannot work there. The
pass-20 M1 warning that names the external-scheduler commands, which is the
thing an operator on such a host actually needs, is on the other branch and
never prints.

`seal` is worse, because it mutates first. Modelled on the same host shape:

```
==> Ingested carlos db credentials into the bundle (carlos.properties keeps a __SEALED__ placeholder)
==> Ingested drugref db credentials into the bundle (drugref2.properties keeps a __SEALED__ placeholder)
==> Installing …/carlos-secrets.service
ERROR: systemctl daemon-reload failed for carlos-secrets.service — … fix the unit (journalctl -u carlos-secrets.service) and re-run 'carlos-ctl seal' (idempotent).
seal exit=1
--- resulting state ---
db_password=__SEALED__
rendered /run fragments: 0
plaintext restic.env present: NO-shredded
```

That is the pass-20 H2 end state — both properties files on `__SEALED__`, the
plaintext shredded, zero `/run` fragments, so the app pod dies on its
`carlos-init` `__SEALED__` guard at the next start — reached through the
branch pass 20 believed was safe. It is loud rather than silent, but the
advice cannot be followed and every re-run fails identically; the inline
render that the no-systemctl path performs is never reached.

The same shape hits the rest of the family: `rotate obs` takes the
`systemctl --user restart` branch, fails, and leaves the stores on the OLD
credential (pass-20 M2 again); `restart_app_and_waf` skips its
`kube play --replace` fallback; and `play`'s pod start would refuse with
"systemd user daemon-reload failed — refusing to start the pods" instead of
falling back, on a host where the quadlets exist (the playbook installs them
unconditionally).

**Fix.** One predicate, `Runner.systemd_running()`, used at every site that
was asking "does this host have systemd": `have("systemctl")` **and**
sd_booted(3)'s own test — `/run/systemd/system` is a directory, which systemd
creates only while it is running as the init system. Both host shapes now take
the documented fallbacks. The probe path is a Settings knob
(`CARLOS_SYSTEMD_RUNTIME_DIR`, default `/run/systemd/system`) so both suites
can model both shapes; `tests/unit/conftest.py` redirects it with the other
host paths (keeping the unit suite's "systemd works" model machine-independent),
and `tests/run-tests.sh` gained six cases driving seal / the timer arming /
`rotate obs` on a **full** stub PATH — systemctl stub included — with the
runtime dir pointed at a path that does not exist, so each one proves the
fallback fired because systemd is unusable rather than because the tool was
missing. `tests/unit/test_runner.py::TestSystemdRunning` pins the predicate
itself, including that the default probe path stays `/run/systemd/system`.
README documents the distinction, and the monitor's pod-unit message no
longer says "systemctl not found on the monitor's PATH" (it is found; the
manager is what is missing).

Verified live on the same instance, before and after:

```
# pre-fix                                        # post-fix
play  → EXIT=1, five impossible                  play  → PLAY_EXIT=0, one warning naming the
        "systemctl start <timer>" warnings               external-scheduler commands
seal  → exit 1, __SEALED__, 0 fragments          seal  → exit 0, both /run fragments rendered
```

and the end state — sealed instance, all six rotations applied — still
serves: `check` 42/3, front door 302 + 200 through the WAF, Playwright 14/14.

## Environment deviations (what this sandbox could NOT prove)

- **No systemd as PID 1.** The quadlet units, the root timers, boot-time guard
  ordering and `enable`/`down --disable` were not exercised as live systemd
  units. `loginctl`/`systemctl` were shimmed for the provisioning run only
  (the role asserts both and waits for `/run/user/<uid>`); every `carlos-ctl`
  invocation ran against the host's real, non-functional systemctl.
- **Container healthchecks never run.** podman drives them from transient
  systemd timers, so every container sits at `Health: starting` forever and
  each gated container costs ~180 s of `_NEVER_RAN_GRACE` per `play`. The
  fallback worked exactly as designed for all four.
- **No journald.** podman's `journald` log driver accepts and discards every
  line, so `carlos-ctl logs` returns nothing and the log-stream freshness
  checks cannot pass.
- **TLS-intercepting egress proxy that serves CONNECT only.** The image builds
  ran with `CARLOS_EXTRA_CA_BUNDLE` pointed at the proxy CA — the documented
  hook, unmodified. The runtime stages' `apt-get` needed a local
  HTTP→HTTPS-upgrading forward proxy in front of it; that is a property of the
  sandbox's egress policy, not of the Containerfiles.
- **`ss` was absent for the first plays**, so the host port-in-use preflight
  skipped with its documented warning; iproute2 was installed part-way
  through, after which it ran.

## Conclusion

The topology went from a bare host to a serving, sealed, backed-up CARLOS EMR
through the documented tooling, and every backup tier — including the
destructive restore drill — passed. The three findings are all in the same
seam: what the project believes about its own test and host environments.
H1 means the suite that carries twenty passes' worth of regression coverage
has not run in CI since pass 18; H2 means seven of its assertions — the ones
pinning pass 20's most recent fixes — could only ever pass on a host without
systemd installed, and on a systemd host would instead drive the real system
manager under sudo; H3 means the fallbacks those assertions exist for did not
engage on the host shape they are most likely to meet, costing an operator a
`play` that can never go green and a `seal` that shreds the plaintext and
leaves the EMR unable to start. All three are fixed here, with regression
coverage in `tests/run-tests.sh` (341 → 347 assertions, 0 failing),
`tests/unit/test_runner.py` (586 → 590) and a static gate on the no-systemd
model itself, and every one verified live on the deployment.
