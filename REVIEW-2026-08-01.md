# carlos-podman — sixth-pass review + live end-to-end test report (2026-08-01)

Scope: full review of `carlos_ctl/`, the Ansible role + all templates, both
Containerfiles, `conf/`, the dev path (`examples/`, `scripts/dev-setup.sh`),
and docs — **plus a live end-to-end exercise** in a rootful-podman sandbox
(podman 4.9.3, Ubuntu 24.04, no systemd): real image builds from source,
`podman kube play` of the dev spec against `carlos-emr/carlos@af909f50` +
`drugref2026@101063bb`, the Ontario Flyway schema, the app repo's Playwright
login suite, and a systematic drive of every `carlos-ctl` verb. Everything in
`REVIEW-2026-07-31.md` and the fifth-pass fix commit was re-checked as fixed
and is not re-reported.

## Findings fixed in this pass

**H1. `carlos-ctl build` could not build on any Ansible-provisioned host.**
The role installed only the two Containerfiles + the CA placeholder into
`$EMR_HOME/build`, but both Containerfiles `COPY conf/...` files that were
never staged there — every role-context build failed at those steps. Found by
running a real build (the stub suite records podman argv; CI never builds).
*Fixed*: the build-context install task now stages
`conf/tomcat/{server,context}.xml` and
`conf/drugref/{server.xml,drugref2-context.xml}`; verified by building both
images from a directory containing exactly the role-installed file set.

**H2. The role-rendered Caddyfile is unreadable by the logview container.**
The render is 0600 (correct — it embeds a bcrypt hash) but no task maps it to
the caddy uid inside the userns; caddy runs uid 10013 with drop-ALL (no
DAC_OVERRIDE) and EACCESes at config load — the authenticated PHI log view
crash-loops on every provisioned obs-enabled install. Every prior live test
fabricated the Caddyfile 0644, which any uid can read — only the Ansible
render is 0600, which is how five passes missed it. *Fixed*: a
`podman unshare chown 10013:10013` convergence task after the render
(mirroring the existing `exporter.my.cnf` precedent) plus the same
convergence in `play`'s obs preflight.

**M1. The build's nofile handling was wrong in both directions.**
*(Follow-up, same day: `-Dmaven.compiler.fork=true` — the configuration this
pass verified end-to-end — was made the Containerfile default and `-T 1C`
dropped (no parallelism on a single-module WAR), restoring 4096 as a
verified-working floor; the stock Containerfile was then re-built at a hard
4096 cap to prove it.)* The
QUICKSTART claimed "≥ 4096 is the verified-working floor"; a real
`carlos-ctl build` of current develop at a hard limit of exactly 4096 **died
~20 minutes in** with `Too many open files` inside javac. And unlike the
QUICKSTART's manual command, `carlos-ctl build` passed no `--ulimit` at all.
*Fixed*: the build now measures the service user's hard limit across the same
runuser boundary the build runs under, passes
`--ulimit nofile=<min(65536, hard)>` to both `podman build`s, and warns below
8192; QUICKSTART's floor claim corrected. (3 regression tests.)

**M2. `--stop-datetime` past-chain-end guard computed the stop epoch in the
host's timezone** while `mariadb-binlog` evaluates it in the DB container's
(`TZ`, default America/Toronto) — on a UTC host the guard silently passed
targets it exists to refuse (silent under-restore) or spuriously refused good
ones. *Fixed*: `stop_datetime_epoch()` interprets the instant in the
container zone via `zoneinfo`, degrading loudly to guard-skip on an unusable
zone. (3 regression tests.)

**M3. Go-live/cert-restart markers were written umask-subject inside the
files-snapshot tree.** A `play` from the QUICKSTART's documented `umask 077`
shell left `.deployed`, `guard/deployed`, `guard/accept-empty-datadir`, and
`.cert-restart-needed` root-0600 under `container/` — unreadable inside the
rootless restic userns, failing **every subsequent nightly files snapshot**
until someone chmods two empty marker files. Same class as the fifth-pass
`.repo-posture`/DR-env fixes; these writers were missed. *Fixed*: explicit
0644 after each write.

**M4. One non-UTF-8 byte in `carlos-app.env` killed every verb.**
`Settings()` decoded the env file strictly and is constructed before verb
dispatch — a pasted cp1252 dash crashed `monitor` before its crash-relay
exists and `alert` (the OnFailure dispatcher itself): the entire paging
pipeline down from one byte. *Fixed*: `errors="replace"` on the env file, the
alert sidecar, and the registry reads (dirty values still fail closed
downstream). (1 regression test.)

**L1. Obs-store probes honored ambient HTTP proxies.** `store_curl` (every
VictoriaMetrics/VictoriaLogs/vmalert loopback probe) lacked the
`--noproxy "*"` the front-door probes pass — a proxied triage shell got walls
of false store-unreachable FAILs and false pages that then armed the
throttle against the real event. *Fixed*: `--noproxy "*"` at the chokepoint.

**L2. vmalert's in-pod listen port is templated from its host-port variable**
while its four pod-mates bind fixed in-pod ports — a value like 8428 passed
the variables-only uniqueness assert, then crash-looped the obs pod.
*Fixed*: an assert rejecting the fixed in-pod listener ports (8428, 9428,
9100, 9443).

**L3. `HL7_A04_GENERATION=true` was rendered against a directory that exists
in no image and is mounted by no pod** (read-only root) — every new-patient
registration logged an A04 failure while the toggle read enabled (dead-green
integration; verified in the app: `DemographicDaoImpl` → `HL7A04Generator`
on every save). *Fixed*: new `carlos_hl7_a04_generation` knob, default off,
with the dev-setup/QUICKSTART renders updated in lockstep.

**L4. Config↔image contract gaps signposted.** The rendered
`carlos.properties` points at `/usr/bin/wkhtmltopdf` and a PGP wrapper +
keyring that the shipped image does not contain (runtime stage installs only
tini + the mariadb client) — eForm→PDF conversion and PGP export cannot work
in-image (both confirmed: the app shells out via `ConvertToEdoc`, and live
logs showed the Selenium/Chromium eform-PDF path failing on the read-only
root too). *Fixed with honest comments* at both template sites; installing
the binaries is a deliberate site/image decision left open.

**L5. Keytool CA-import loop swallowed every failure except the last
piece's** (a `for` chain's status is the last iteration's) — a corrupt cert
mid-bundle produced a bare PKIX failure 20 minutes later, or a build that
trusted less than the operator staged. *Fixed*: skip cert-free preamble
pieces, `|| exit 1` on real import errors (both Containerfiles).

**L6. `down` (podman branch) counted a `pod stop` cleanup error as
"did NOT stop"** even when every container was already down — `pod stop`
exits nonzero for post-stop cgroup-teardown errors too (verified live: rc
125, pod state Exited), so a successful maintenance stop returned rc 1 and
blocked `down && umount` scripting. The systemd branch already rechecked
`is-active`; the podman branch did not. *Fixed*: recheck the pod's inspected
state after a failed stop — only a pod not affirmatively
Exited/Stopped/Dead counts (unknown state stays a failure, fail-safe).
(2 regression tests.)

**L7. Stale/misleading docs corrected**: `zz-carlos.cnf`'s "REMAINING
LIMITER" block described the retired script pipeline (the live Flyway
baseline is utf8mb4/InnoDB throughout — verified, 0 hits); the CARLOS
Containerfile now carries a standalone-run caveat (loopback-pinned 8080 +
pod-generated keystore make a bare `podman run` healthy-but-unreachable).

## Findings verified and REJECTED during this pass

- *"`io.podman.annotations.pids-limit` is a no-op below podman 5.5"* —
  *disproven live*: the deployed dev pod on podman 4.9.3 shows
  `PidsLimit=2048` in `podman inspect`.
- The monitor's silent non-tty exits, `pma`'s foreground blocking, `podman
  restart` not picking up rotated credentials (initContainers only re-run on
  pod replace — exactly why `rotate`/`play` messages say what they say), and
  the `check` FAILs against the dev topology are all **as designed** and
  documented.

## Upstream (carlos-emr/carlos) notes from live testing

- `formRourke2009` is created `ENGINE=Aria` by `on/V1.0.1__on_schema.sql`
  (and the BC V1.0.6 restore file) in an otherwise all-InnoDB utf8mb4
  baseline — `carlos-ctl backup` correctly refuses the nightly dump over it
  (PITR consistency) until `CARLOS_ALLOW_NON_INNODB=1`. Converting it to
  InnoDB upstream would remove the only such exception.
- The eform browser-PDF service (Selenium/Chromium) retries hard at app
  startup; in a read-only-root container without a browser this is steady
  error noise — a config toggle upstream would help containerized deploys.
- The QUICKSTART Playwright caveat about `ignoreHTTPSErrors` is fixed
  upstream (all `request.newContext()` calls carry it).

## Sandbox deltas (not repo defects)

Rootful podman (`SERVICE_USER=root`), no systemd (quadlet/timer paths
observed to fail loudly and degrade as designed), no TPM, egress via a
TLS-intercepting proxy (exercised the EXTRA_CA hook for real), nofile hard
limit capped at 4096 by the sandbox (the M1 evidence; the successful build
used a forked-javac variant to fit under the cap — the stock Containerfile
compile needs more than 4096 regardless).
