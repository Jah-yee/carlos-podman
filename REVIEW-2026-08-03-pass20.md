# carlos-podman — twentieth-pass review + live end-to-end test report (2026-08-03)

Scope: a fresh review of `carlos_ctl/`, the Ansible role, the Containerfiles and
the four gate suites, plus a **live end-to-end deploy of the full production
topology on a bare host** — `carlos-ctl setup` → `ansible/site.yml` → both
images built from source with `carlos-ctl build` → all three pods started →
the Ontario Flyway schema and the DrugRef database loaded through
`carlos-ctl db` → `carlos-ctl check` → the app repo's Playwright suites through
the WAF → every backup tier including the point-in-time restore drill → the
complete credential-rotation and sealing matrix → a systematic drive of the
**whole** `carlos-ctl` verb matrix. Everything reported fixed through
`REVIEW-2026-08-03-pass19.md` was treated as baseline; only NEW findings are
reported here.

Environment: podman **4.9.3** (the documented floor), Ubuntu 24.04, **no
systemd as PID 1**, cgroup v1, TLS-intercepting egress proxy, `nofile` hard cap
4096, native overlay storage.

**Deliberate difference from pass 19.** Pass 19 shimmed `systemctl` so the
deploy exercised carlos-ctl's *primary* (systemd) branch. This pass removed
`systemctl` from the host entirely, so the same deploy ran on the **documented
no-systemd fallback** (README, "Each pod runs as a systemd service": `play`/
`down` fall back to plain rootless `podman kube play`/`kube down`). That path
had never been exercised end to end — four of the five findings below live in
it.

## New findings

### H1 (HIGH): every root → service-user call fails from `/root`, so on a healthy host `check` reports the deployment missing and `down` reports success while everything keeps running

`Runner.podman_user_argv` crosses into the rootless engine with
`runuser -u <SERVICE_USER> -- env XDG_RUNTIME_DIR=… podman …`. `runuser`
**keeps the caller's working directory** and hard-fails when the target user
cannot enter it:

```
# cd /root && runuser -u carlos -- env XDG_RUNTIME_DIR=/run/user/996 podman ps
cannot chdir to /root: Permission denied      # rc 1, podman never runs
```

`/root` is mode 0700 and is the working directory of every `sudo -i` / root
login shell — i.e. exactly where an operator runs `sudo EMR_HOME=… carlos-ctl
…`. Every previous pass ran the CLI from a repo checkout under a
world-executable path, which is why 19 passes never hit it.

Measured live on the fully-provisioned instance, *before* the fix:

```
# cd /root && EMR_HOME=/usr/local/emr carlos-ctl check
FAIL carlos-app pod missing — 'carlos-ctl play'
FAIL carlos-net network missing — run the provisioning playbook
FAIL carlos-edge network missing — run the provisioning playbook
FAIL container not running: carlos-app-db
… (every container)
# cd /root && EMR_HOME=/usr/local/emr carlos-ctl status
cannot chdir to /root: Permission denied
cannot chdir to /root: Permission denied
…                                              # empty tables, exit 0
```

Both networks existed and all three pods were serving. The blast radius is
not only a wrong diagnosis:

- **`down` reports a false green.** In the no-systemd branch `podman kube down`
  is `quiet=True` and `podman pod exists` returns nonzero, so every pod is read
  as already-absent, `stop_failures` stays empty and `cmd_down` returns **0**
  with MariaDB still running — the exact false success the rc-gating exists to
  prevent for `carlos-ctl down && umount <datadir>` maintenance scripting.
  Measured live against the running stack with the pre-fix code:

  ```
  # cd /root && EMR_HOME=/usr/local/emr carlos-ctl down
  ==> target: instance=carlos  EMR_HOME=/usr/local/emr  env=…/carlos-app.env
  # echo $?
  0
  # podman ps --format '{{.Names}}' | wc -l
  15                     # every container, including carlos-app-db, still up
  ```

  With the fix, the same command from the same directory stops all three pods
  and leaves 0 containers running.
- `play` refuses with "no 'carlos-edge' network — run the provisioning playbook
  first" on a host whose networks are fine.
- `logs`, `db`, `db-dump`, `backup`, `monitor`, `pma` — everything that touches
  podman — fails the same way, with an error message that names neither
  carlos-ctl nor the fix.

**Fix.** Pin the crossing's working directory to `/` in `Runner.run` (the one
chokepoint every crossing goes through). The rule is argv **membership**, not
`argv[0]`: `cmd_pma` wraps the crossing as
`timeout -k 10 <ttl>m runuser -u <user> -- podman run …`, so an `argv[0]`-only
test would have left the break-glass verb broken. Nothing in the tree is
cwd-relative and `/` is world-executable, so the pin costs nothing.
Regression coverage: `tests/unit/test_runner.py::TestCrossUserCwd` spawns a
fake `runuser` from a scratch directory and asserts the child really starts in
`/` (and that a non-crossing call still inherits the caller's cwd).

Two path values are normalized to absolute as part of the same fix, because
they are argv tokens for the now-cwd-pinned child: `Settings.emr_home` and the
`CARLOS_BUILD_DIR` dev override. A relative value for either would previously
have resolved against the caller's directory on both sides of the boundary;
with the pin it must be anchored once, in the CLI process.

### H2 (HIGH): on a host without systemd, `carlos-ctl seal` reports success and takes the EMR down at the next pod start

`cmd_seal` ingests the live DB credentials into the SOPS+age bundle, replaces
them in `carlos.properties`/`drugref2.properties` with the literal
`__SEALED__`, writes `<instance>-secrets.service` — and then does the
`daemon-reload`/`enable`/`start` **inside `if runner.have("systemctl")`**, with
no `else`. On a host with no systemctl the whole block was skipped in silence:
the unit exists, nothing ever runs it, and `secrets render` (its `ExecStart`,
and the only thing that materializes the `/run` credential fragments) never
happens.

Measured live, pre-fix, on the serving instance:

```
==> Ingested carlos db credentials into the bundle (carlos.properties keeps a __SEALED__ placeholder)
==> Ingested drugref db credentials into the bundle (drugref2.properties keeps a __SEALED__ placeholder)
==> Installing /etc/systemd/system/carlos-secrets.service
==> Secrets consolidated into …/secrets.enc.yaml (SOPS+age single master)
# exit 0
# ls /run/carlos-emr/
(empty)
```

The next start of the app pod then died on the in-pod guard — the pod spec's
own load-bearing check — and the EMR was **down**:

```
Error: init container af066b22fed2… exited with code 1     # carlos-init __SEALED__ guard
carlos-app-carlos-init   Exited (1)
```

An operator following the README's step 7 (`seal`) on a no-systemd host
therefore gets a green seal and an EMR that refuses to start at its next
restart or reboot, with the plaintext already shredded.

**Fix.** Give the `have("systemctl")` test an `else` that performs the render
**inline** — it is literally the unit's `ExecStart` — and states the standing
requirement that something must run `carlos-ctl secrets render` before the pods
on every boot (the fragments live in tmpfs). Verified live: the fixed `seal`
renders both fragments and the previously-refusing pod starts:

```
==> no systemctl — rendering the sealed credential fragments inline (the installed unit cannot be started on this host)
WARNING: no systemd on this host: NOTHING re-renders /run/carlos-emr (tmpfs) at boot — run 'carlos-ctl secrets render' from your boot scheduler BEFORE the pods start, or the app dies on its __SEALED__ guard
# ls -l /run/carlos-emr/
-rw------- 1 carlos root 64 carlos-db.properties
-rw------- 1 carlos root 61 drugref-db.properties
# podman kube play --replace … → carlos-app-carlos up
```

`cmd_play` carried the same gap for the same reason (it starts the secrets unit
only when systemctl exists) and got the same inline fallback.

### M1 (MEDIUM): a no-systemd `play` goes green with NO backup, binlog, document, restore-drill or monitor schedule — and says nothing

`start_instance_timers` ends with the go-live markers and then:

```python
if not runner.have("systemctl"):
    return True          # ← silent
```

So on the documented fallback path `play` writes `container/.deployed` and
`container/guard/deployed`, exits 0, and the instance has **no scheduled
backups, no binlog shipping, no document snapshots, no restore drill, no
monitor sweep and no boot-time datadir guard**. Nothing downstream covers it
either: `check`'s runtime-floor loop *skips* the systemd floor when the tool is
absent (`if argv[0] != "podman" and not runner.have(argv[0]): continue`), and
the monitor's own missing-unit sweep returns early without systemctl — and the
monitor is itself one of the jobs that never runs.

Measured live: the deploy completed, `container/.deployed` and
`container/guard/deployed` were written, and the entire play output contained
no mention of the schedule; `check` then printed 41 passed / 3 failed with the
three failures unrelated (log-stream freshness, see the deviations below).

Every *other* no-systemd branch in the tree is loud about it — `cmd_down` logs
"no systemd pod units on this host", `cmd_enable` raises, `tlsops` warns that
it cannot restart the cert consumers — so this was an inconsistency as much as
an omission.

**Fix.** `play` now warns once per run, naming the exact commands an external
scheduler has to fire (`backup full` nightly, `backup binlogs`/`backup docs`
every 15 min, `backup verify` weekly, `monitor` hourly, `guard` before the pods
at boot), and `check` carries the matching posture warning so the verb an
operator runs when something feels wrong can actually say it. Deliberately a
warning and not a hard failure: `play`/`down` on plain `podman kube play` is a
documented mode, and an external scheduler is invisible to carlos-ctl, so a
FAIL could never be cleared.

### M2 (MEDIUM): `rotate obs` moves every client to the new credential but not the stores on a no-systemd host — and still reports success

Found by review while auditing the same class as H2/M1, and confirmed against
the live instance. `_rotate_obs_http` ends by restarting the pods so every
consumer moves together. The app+waf half goes through
`dbops.restart_app_and_waf`, which has a `podman kube play --replace`
fallback; the **obs** half was a bare
`if runner.have("systemctl") and <quadlet exists>` with no `else`. So on a
no-systemd host the canonical file, the podman secret, the vector sink and the
Caddyfile all get the new credential, VictoriaMetrics/VictoriaLogs/vmalert keep
serving with the old one, and the verb still prints
`Rotated the obs-store credential (stores, vmagent, vector, log view)`.
The whole metrics and log pipeline 401s — silently, until someone happens to
run `play`. No data loss (the credential is regenerable), but the PHI-adjacent
log store stops receiving and `check`/`monitor` only surface it on their next
run.

**Fix.** The same `kube play --replace` fallback the app/waf half already
carries, plus a warning when it fails. Regression coverage in
`tests/run-tests.sh` (a stub PATH with every binary except `systemctl`).

### H3 (HIGH): on a host without systemd, `carlos-ctl uninstall` crashes mid-decommission and leaves the live credentials, the front-door DNAT and the host default-deny firewall behind

The quadlet-cleanup block runs `runner.systemctl_user(["daemon-reload"])`
**without** a `have("systemctl")` gate, and its enclosing
`contextlib.suppress(CtlError)` does not catch the `FileNotFoundError`
`subprocess` raises for a missing binary. Measured live at the end of this
pass, on the real instance:

```
==> Decommissioning instance 'carlos' (data preserved)
ERROR: unexpected FileNotFoundError: [Errno 2] No such file or directory: 'systemctl'
# echo $?
1
```

The verb had already stopped the pods and removed the root units and the
quadlets, and then aborted **before** every remaining cleanup step. State
left on the host, verified item by item:

| left behind | why it matters |
| --- | --- |
| `table ip carlos-nat` | the live `:443 → :8443` front-door DNAT, now pointing at nothing |
| `table inet carlos-hostfw` | a **host-global default-deny input chain** with no CARLOS instance behind it — the exact stale-firewall case `cmd_uninstall` deletes it to avoid |
| `carlos-net`, `carlos-edge` podman networks | name collisions for a later re-provision |
| podman secrets `carlos-db`, `carlos-obs-http` | **live credentials** — the MariaDB root password and the obs-store basic-auth credential — left in the shared service user's secret store (the pass-19 finding, re-created wholesale) |
| `/run/carlos-emr/{carlos,drugref}-db.properties` | the **decrypted** sealed credential fragments, still readable |
| `/etc/tmpfiles.d/carlos-emr.conf` | recreates that /run dir at every boot |
| `/etc/carlos-podman/instances/carlos.{conf,alert.env}` | the instance still shows in `carlos-ctl instances`, and the alert-channel mirror still holds the webhook URL |

…and the only thing the operator was told is the exception's type.

**Fix.** `have()`-gate the user-manager reload, and widen the block's
suppression to `OSError` as well: a decommission must never abort part-way,
because everything after that point is credential and host-claim cleanup.
Verified live — the re-run completed, and afterwards `nft list tables` is
empty, both instance networks and both podman secrets are gone, `/run`, the
tmpfiles.d entry and the registry claim are removed, and the 2.6 GB data tree
plus the 478 MB restic repo are untouched, exactly as the banner promises.
Regression coverage in `tests/run-tests.sh` (six cases on the
systemctl-less stub PATH).

## Environment deviations (what this sandbox could NOT prove)

- **No systemd as PID 1, and `systemctl` removed.** This is what made the two
  silent findings visible, but it also means the quadlet units, the root
  timers, the boot-time guard ordering and `enable`/`down --disable` were not
  exercised as systemd units this pass (pass 19 covered those through a shim).
- **Container healthchecks never run.** podman drives them from transient
  systemd timers, so every container sits at `Health: starting` forever. This
  is the degraded shape `_NEVER_RAN_GRACE` exists for and it worked exactly as
  designed — at the cost of ~180 s of grace per container on every `play`.
- **No journald.** podman's `journald` log driver accepts and discards every
  line, so `carlos-ctl logs` returns nothing and the three log-stream
  freshness checks in `check` (and the waf-5xx surveillance alert in
  `monitor`) fail. That is the checks doing their job.
- **TLS-intercepting egress proxy.** The image builds ran with
  `CARLOS_EXTRA_CA_BUNDLE` pointed at the proxy CA — the documented hook — and
  it worked unmodified.
- **`nofile` hard cap 4096.** `carlos-ctl build` warned at its documented floor
  and both images built anyway (the forked-javac Containerfile).

## Conclusion

The topology went from a bare host to a serving, sealed, monitored, backed-up
CARLOS EMR through the documented tooling, and every backup tier — including
the destructive-restore drill — passed. The five new findings are all in paths a previous pass had no reason to
enter. H1 needs only a root login shell's working directory and silently
inverts the answer of `check` and the exit code of `down`. H2, H3, M1 and M2
are all the same shape — a `have("systemctl")` branch with no `else` — and
between them they cost the operator a running EMR (H2), a decommission that
leaves live credentials and a stale host firewall behind (H3), a deploy with
no backups or monitoring at all (M1), and a metrics/log pipeline that 401s
after a credential rotation (M2). All five are fixed here, with regression
coverage in `tests/unit/test_runner.py` (H1) and `tests/run-tests.sh` (H2,
H3, M1, M2 — thirteen new cases driven on a stub PATH that has every binary
except `systemctl`), and every one of them verified live on the deployment.
