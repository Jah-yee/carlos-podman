# carlos-podman — seventeenth-pass review + live end-to-end test report (2026-08-03)

Scope: a fresh review of `carlos_ctl/`, the Containerfiles and the Ansible
role, plus a **live end-to-end exercise of the FULL production topology** in a
rootless-podman sandbox (podman 4.9.3, Ubuntu 24.04, **no systemd PID 1**,
cgroup **v1**, TLS-intercepting CONNECT-only egress proxy, `nofile` hard cap
4096): real image builds from source, **`ansible/site.yml` run for real**
against an empty instance home, `podman kube play` of the **role-rendered**
app + obs + waf pods against `carlos-emr/carlos@develop` +
`drugref2026@master`, the Ontario Flyway schema (427 tables), the DrugRef
database, the app repo's Playwright login suite, and a systematic drive of the
**complete** `carlos-ctl` verb matrix. Everything reported fixed through
`REVIEW-2026-08-02-pass15.md` (and the sixteenth-pass merge) was treated as
baseline; only NEW findings are reported here.

## Why this pass found deploy-blockers that sixteen passes missed

Every previous live verification stood up the **dev** topology
(`scripts/dev-setup.sh` + `examples/carlos-app-dev.yaml`). That path

- `mkdir -p`s `$EMR_HOME/container/conf/...`, `data/...`, `logs/...` **before**
  the role ever runs, so the role never created those parents and how it
  creates them was never observed (**H1**);
- renders `carlos.properties` and the pod spec with its own in-script Python,
  so the role's `journald-collector.toml` and `scrape.yml` templates were only
  ever *rendered and grepped*, never *loaded by vector/vmagent* (**H3**, **H4**);
- **omits the drugref container entirely** (its own header says so), so the
  DrugRef ↔ MariaDB stack was never actually started (**H5**);
- and every sandbox so far had no working systemd-user manager — which is
  exactly the degraded case whose readiness fallback turns out to be
  unreachable for the last-polled container (**H6**).

Six of the seven findings below are things a **first production install hits
on day one**; five of them stop the deploy or the first login outright.

## New findings

### H1 (HIGH, deploy-blocking): the role creates `$EMR_HOME`'s shared parents root-owned and non-traversable, so the rootless engine cannot mount anything

`ansible.builtin.file` stamps the loop item's `mode:` onto every INTERMEDIATE
directory it has to create, and creates them root-owned. The "Instance
directory tree" loop led with

```yaml
- {path: "{{ carlos_conf_dir }}/waf/certs", mode: "0700"}
```

so on a genuinely fresh host that one entry created `$EMR_HOME`,
`container/`, `container/conf/` and `conf/waf/` as **root:root 0700**; the
`data/mariadb-mnt` 0700 entry did the same to `data/`; and `logs/`,
`metrics/`, `monitor/` were left 0750 **root:root**. The subuid-aware
ownership sweep further down lists only the LEAF directories, so nothing ever
handed those parents over.

Measured live, as the service user:

```
$ podman run --rm -v $EMR_HOME/container/conf/carlos/carlos.properties:/x:ro alpine true
Error: statfs /home/carlos/emr/container/conf/carlos/carlos.properties: permission denied
$ podman run --rm -v $EMR_HOME/data/mariadb-mnt:/x  alpine true   -> permission denied
$ podman run --rm -v $EMR_HOME/logs/carlos:/x       alpine true   -> permission denied
$ podman run --rm -v $EMR_HOME/metrics/vmagent-buffer:/x alpine true -> permission denied
```

Those are the app pod's config, datadir, binlog, log and metric mounts, so
`podman kube play` fails on its first volume and the instance **cannot start
at all**. The same EACCES also broke the role's own two `podman unshare chown`
hand-overs, whose warnings then named the wrong cause (they blame the file's
`owner:group` and the subuid ranges — both of which were correct).

Fixed in `tasks/instance.yml` by declaring the traversal parents FIRST, with
explicit owner/mode: `$EMR_HOME`, `container/`, `backup/`, `run/` root 0755;
`conf/` **root:*service user* 0750** (the service user must TRAVERSE it, but
must not own or write it — `conf/secrets` holds the age recipient and the
encrypted bundle, and a service-user-writable parent would let that directory
be renamed and replaced, the re-encryption-recipient injection vector its own
root ownership exists to close); `data/`, `logs/`, `metrics/` service-user-owned
0750; `monitor/` root 0750 (root-only, no container reads it). Verified live:
after the fix the role re-run repairs the tree, both userns chowns succeed,
and every previously-failing mount probe passes.

Pinned by a new `ansible-checks.sh` gate that requires each shared parent to
be declared, and to be declared BEFORE the first `mode: "0700"` leaf, plus the
exact owner/group posture for `conf/`, `data/`, `logs/`, `metrics/`.
(Mutation-tested: moving the `conf/` entry after the 0700 leaf fails the gate.)

### H2 (HIGH, every re-run of the playbook aborts): a skipped `stat` clobbers `_tls_cert`

`register:` on a SKIPPED task overwrites the variable with the skip result
(`{changed: false, skipped: true}`) — which has no `.stat`. The TLS re-stat
carried `when: _tls_selfsigned is changed`, so on every run AFTER the first
(where the generation task is skipped by its `creates:`) the re-stat was
skipped, `_tls_cert.stat` was destroyed, and the very next task aborted the
whole play:

```
Error while evaluating conditional: object of type 'dict' has no attribute 'stat'
```

The documented change workflow is "edit host_vars → re-run the playbook →
`carlos-ctl play`", so **no provisioned selfsigned instance could apply any
config change**. `--check` cannot catch it: on a fresh check prefix the
generation task always reports `changed`, so the skip branch is unreachable
there. Reproduced live on the second real run and confirmed fixed on the
third (`ok=77 changed=3 failed=0`).

Fixed by making the re-stat unconditional (a stat costs nothing). Pinned by a
gate asserting the re-stat has no `when:`, plus a generic scan for any
conditionally-registered variable dereferenced as `.stat`/`.rc`/`.content`
without an `is defined` / `is skipped` / `| default` guard.

### H3 (HIGH): a `$VAR` **inside a comment** crash-loops the PHI log collector

Vector env-interpolates its config file — comments included — over the RAW
text before parsing it. `journald-collector.toml.j2`'s comment explaining that
very hazard contained the literal `$VAR/${...}`, so vector hard-failed config
load on every default install (the obs profile and store auth are both on by
default, and the block renders only when auth is on):

```
ERROR vector::cli: Configuration error. error=Missing environment variable in config. name = "VAR"
ERROR vector::cli: Configuration error. error=Missing environment variable in config. name = "..."
```

`carlos-obs-logcollect` crash-looped, so the whole journald → VictoriaLogs
pipeline was dead: no shipped logs, nothing in the log view, and `carlos-ctl
check`'s log-stream checks all FAIL with the root cause invisible. Verified
live — removing the two sigils is the entire fix, and the container has been
up ever since.

Fixed by describing both forms in prose instead of showing them. Pinned by a
new gate that TOML-parses the rendered collector config and rejects any
un-doubled `$`.

### H4 (HIGH): an indented Jinja comment makes the vmagent scrape config invalid YAML

Jinja deletes a comment's TEXT but KEEPS the whitespace that preceded it on
that line, and Ansible's `trim_blocks` then eats the newline after the closing
marker. A 6-space-indented `{# … #}` inside the `basic_auth:` mapping in
`scrape.yml.j2` therefore prepended its own indentation to the next line:

```yaml
    basic_auth:
            username: "obs"
      password_file: /etc/obs-auth/password
```

vmagent hard-failed at startup with
`cannot unmarshal data: yaml: line 39: did not find expected key` and
crash-looped (2414 restarts in ten minutes, measured), so on every default
install there were **no metrics at all** and every vmalert rule — the entire
metric-alerting half of the monitoring design — never evaluated. The app pod
runs on the journald log driver, so `podman logs` showed nothing and the
failure was silent.

Fixed by moving the comment to column 0. Pinned by the same new gate, which
now YAML-parses the rendered `scrape.yml` and `vmalert-rules.yml`.

### H5 (HIGH, deploy-blocking): DrugRef cannot start against MariaDB, so `play` can never green

DrugRef's `spring_config.xml` sets no `hibernate.dialect`, so Hibernate 6
auto-detects one from JDBC metadata — and DrugRef bundles
`mysql-connector-j 9.1.0`, whose `DatabaseMetaData.getSQLKeywords()` runs

```sql
SELECT WORD FROM INFORMATION_SCHEMA.KEYWORDS WHERE RESERVED=1
```

MariaDB's `information_schema.KEYWORDS` has only `WORD`. Verified against the
pinned `mariadb:11.4.12`:

```
ERROR 1054 (42S22): Unknown column 'RESERVED' in 'WHERE'
```

so metadata access fails → `Unable to determine Dialect without JDBC
metadata` → the `entityManagerFactory` bean fails → `Context [/drugref2]
startup failed` → Tomcat serves 404 forever. The pod's drugref
startup/liveness probes deliberately REJECT 404 (an earlier finding), so
`wait_app_ready` never greens: **`carlos-ctl play` cannot succeed on a stock
install** — no `.deployed` marker, no timers, no backups, no monitoring — and
drug/interaction checking is dead. `rebuild` and `rollback`, which trust
play's exit code, inherit it.

Fixed by passing `-Dhibernate.dialect=org.hibernate.dialect.MariaDBDialect`
and `-Dhibernate.boot.allow_jdbc_metadata_access=false` in the drugref
container's `CATALINA_OPTS` (pod spec) and in the image's default
`CATALINA_OPTS` (standalone runs). Verified live: `GET /drugref2/` went from
404 to **200**, and the next `play` reached its post-readiness bookkeeping.
Pinned by a gate requiring both flags in the rendered pod spec AND in
`Containerfile.drugref`.

### H6 (HIGH): the readiness gate fails a healthy deploy because the last-polled container's deadline is already spent

`wait_app_ready` computes every deadline absolutely from ONE `t0` (correct in
principle — the containers start concurrently) but polls them SERIALLY. The
waf carries the SMALLEST budget (420 s) and is polled LAST, so everything
spent verifying db + carlos + drugref comes out of it. On a host where
podman's healthcheck timers never run — the degraded case `_NEVER_RAN_GRACE`
was added for in pass 15 — each of the three preceding containers burns 180 s
of grace before its fallback probe fires, ~540 s, so the waf's deadline is
gone before its first poll and its fallback can never run.

Measured live, with the front door serving **200** and the waf's own declared
probe returning 0:

```
WARNING: the carlos-app containers did NOT all reach 'healthy' within
READY_WAIT_SECONDS — the app is not serving, so NO go-live markers were
written and NO timers were armed.
```

That is the S13 failure mode (a live PHI stack with backups and monitoring
silently disarmed, and an operator told to roll back a good build), re-created
for the waf.

Fixed by flooring each DEFAULT-budget deadline at "enough time, from the
moment this container's own polling starts, for the fallback path to run at
all" (`_NEVER_RAN_GRACE` + one poll interval). The floor is deliberately NOT
applied when `READY_WAIT_SECONDS` is set explicitly — that knob is the
operator's (and the hermetic suite's) direct statement of patience. Verified
live: the next `play` probed the waf, greened, wrote `.deployed`, recorded the
schema fingerprint and went on to the timer step. Pinned by three unit tests
(the last container still gets a probe; a failing probe still fails the gate;
an explicit `READY_WAIT_SECONDS` is never silently extended) — mutation-tested
against the pre-fix code.

### H7 (HIGH, first-login blocker): `IS_PIN_ENCRYPTED=yes` makes the seeded administrator account unable to log in

The role derived `IS_PIN_ENCRYPTED=yes` for a fresh datadir, reasoning that a
fresh install has "no stored PINs to break". The premise is false:
provisioning runs BEFORE the schema load, and **the schema load is what
creates the bootstrap administrator** — the Flyway seed
(`migration/on/V1.0.2__on_data.sql`, and the BC equivalent) inserts
`carlosdoc` with a **cleartext** PIN. `LoginCheckLoginBean.authenticate()`
encrypts the SUBMITTED pin before comparing it to the stored one, so the
comparison can never match and the account is refused with "Pin-local
needed" — QUICKSTART step 5 and the README's "First login" are unreachable on
every fresh Ontario or BC install.

Proved live by converting only the stored PIN to the encrypted form: the
identical login POST went from

```
302 -> /carlos/index?login=failed
```

to

```
302 -> /carlos/provider/providercontrol?year=2026&month=8&day=3&…
```

Fixed by defaulting `carlos_pin_encrypted` to `no` (cleartext) for fresh and
existing datadirs alike — the format upstream's own seed writes. The choice
costs nothing real: `Misc.encryptPIN` is a `@Deprecated` unsalted running-sum
over the characters ("Do not rely on this for securing sensitive data", its
own javadoc), i.e. obfuscation, not protection. An explicit
`carlos_pin_encrypted: 'yes'` is still honored verbatim (and then every seeded
PIN must be converted by hand). The existing PIN-derivation gate was rewritten
to assert the new contract in all four cases (fresh, existing, empty override,
explicit `yes`).

### M1 (MEDIUM, documentation): following the DrugRef load instructions makes every nightly backup refuse

The README's DrugRef section tells the operator to load
`database/mysql/development-drugref.sql` — whose 17 `CREATE TABLE`s are **all
`ENGINE=Aria`**. `backup full`'s engine audit then refuses the nightly dump:

```
WARNING:   drugref2.cd_drug_product [Aria]  (convert to InnoDB)
…15 more…
WARNING: refusing the nightly dump: non-InnoDB tables break the
point-in-time-recovery consistency contract — convert them to InnoDB, or set
CARLOS_ALLOW_NON_INNODB=1 …
```

The refusal is CORRECT (a non-transactional table cannot participate in the
`--single-transaction` snapshot the PITR anchor depends on), and it names the
remedy — but nothing warns the operator at the point where they create the
problem, and `backup verify` then fails too because no `db` snapshot exists.
On a fresh install this means the FIRST nightly backup fails, and the
freshness stamps `play` seeded keep the monitor quiet for the first 26 hours.
`oscar.formRourke2009` is correctly recognized as the one KNOWN-unconvertible
table and does not trigger the refusal.

Documented in the README's DrugRef section (convert the drugref2 tables to
InnoDB right after the load, with the one-liner to do it) rather than
"fixed": the audit is behaving as designed, and silently converting an
operator's tables inside a backup run would violate the data-safety contract.
The added recipe was run verbatim on the live instance — afterwards
`formRourke2009` is the only non-InnoDB table left, `backup full` completes
(dump staged + footer-verified, documents + config, binlogs shipped,
retention + `restic check`), and `backup verify` passes the full restore
drill: docs snapshot byte-verified, throwaway tmpfs MariaDB, dump loaded,
**binlog replay from the recorded anchor** (`binlog.000010:339`), core tables
present.

## Environment notes (not defects in this repo)

- **No systemd PID 1.** Every `systemctl` path legitimately fails here: the
  quadlet branch of `play` refuses (correctly) with "systemd user
  daemon-reload failed", so the direct `podman kube play` fallback was
  exercised instead, and `start_instance_timers` reports every timer as
  unstartable — which is why `play` still exits 1 at the very end, after
  writing the go-live markers. Reported as such, not as findings.
- **cgroup v1**: rootless resource limits are silently unenforced (podman says
  so per container); the pod specs' limits are ignored here.
- The egress proxy serves CONNECT only, so a local HTTP→HTTPS upgrading
  forward proxy was placed in front of it for `apt` inside the image builds.
  Nothing in this repo is involved.
