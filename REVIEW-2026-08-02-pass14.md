# carlos-podman — fourteenth-pass review + live end-to-end test report (2026-08-02)

Scope: a fresh review of `carlos_ctl/`, the Containerfiles and the Ansible
role, **plus a full live end-to-end exercise** in a rootless-podman sandbox
(podman 4.9.3, Ubuntu 24.04, **no systemd PID 1**, TLS-intercepting egress
proxy, `nofile` hard cap 4096): real image builds from source, `podman kube
play` of the dev spec against `carlos-emr/carlos@af909f50` +
`drugref2026@101063bb`, the Ontario Flyway schema (427 tables), the app repo's
Playwright login suite (twice), and a systematic drive of the **complete**
`carlos-ctl` verb matrix — every verb in `cli.py`'s dispatch. Everything
reported fixed through `REVIEW-2026-08-02-pass13.md` was treated as baseline;
only NEW findings are reported here.

The pods ran **rootless as the `carlos` service user** (the production
topology), so every `runuser` / `XDG_RUNTIME_DIR` / subuid boundary in
`carlos_ctl.runner` was exercised for real rather than as root.

## New findings

### H1 (HIGH, observability). `db-users` / `rotate db` / play's auto-provisioning permanently break the mysqld-exporter credential file — MariaDB metrics are gone from the first deploy and `play` cannot repair them. **Fixed.**

**What happened.** The mysqld-exporter runs as container uid **65534** and
reads its own `conf/metrics/exporter.my.cnf` at mode **0600**, so on the host
the file must be owned by the service user's subuid mapping for 65534. Because
a host-side `chown 65534` cannot express that mapping, both the role and the
CLI hand the file over in two steps: chown it to the service user, then
`podman unshare chown 65534:65534` inside the rootless userns.

`dbops.provision_db_accounts` writes a fresh **root:root** replacement of that
file on every credential provisioning, and then did:

```python
os.chown(s.exporter_mycnf_file, pwd.getpwnam(s.service_user).pw_uid, -1)
```

`-1` means "leave the group alone", so the file ended up **`carlos:root`**.
Host gid 0 is **not** in the service user's userns id_map, and `chown(2)`
refuses a file whose current owner *or group* is outside the map — so the very
next `podman unshare chown` failed with `EPERM`, every time. Measured live on
the running instance:

| host ownership of the file | `podman unshare chown 65534:65534` |
|---|---|
| `root:root` (0:0) | **EPERM** |
| `carlos:root` (1001:0) — what the code produced | **EPERM** |
| `carlos:carlos` (1001:1002) | ok → `231069:231069` |

The service user's map is `uid 0→1001 (1)`, `uid 1→165536 (65536)` and the
same for gids: neither host uid 0 nor host gid 0 appears in it.

**Why it matters, and why it never recovered.** Least-privilege provisioning
is the **default** on the first `carlos-ctl play` (`maybe_provision_db_users`),
so an obs-enabled install breaks its own metrics file during its first deploy.
The exporter then cannot read a 0600 file owned by container-root: `mysqld_up`
never appears, and every vmalert rule keyed on MariaDB metrics (MysqlDown and
friends) silently never evaluates. Both warning messages point the operator at
`carlos-ctl play` — but `cmd_play`'s convergence chown had **no pre-chown at
all**, so it re-ran the identical failing `unshare chown` and reported the same
warning. The only thing that recovered it was a full playbook re-run, whose
subuid-aware ownership sweep sets uid **and** gid.

The Ansible role had the same defect one layer up: its pre-chown was
`chown "{{ carlos_service_user }}" <file>` — coreutils `chown` with no group
leaves the group untouched, i.e. root on a root-rendered file. It happened to
work only because the ownership sweep (`chown -h user:user`) runs earlier in
the same play and had already fixed the group; the first `carlos-ctl` rewrite
after provisioning undid that and nothing put it back. The log-view
`Caddyfile` (container uid **10013**, drop-ALL, no `DAC_OVERRIDE`) sits behind
the identical two-step and the identical bare-`chown` pre-step, so a
root-written replacement there crash-loops the PHI log view the same way.

**Fix.**

- New `util.chown_to_service_user(path, user)` — sets **both** uid and gid from
  `pwd`, returns False instead of raising. The docstring carries the id_map
  rationale so a future `-1` cannot be reintroduced as "the group doesn't
  matter".
- `dbops.provision_db_accounts` uses it, and warns distinctly when the
  hand-over itself fails (previously indistinguishable from a failed userns
  chown).
- `lifecycle2.cmd_play` now **repairs** before it maps, for the exporter cnf
  and the Caddyfile alike — `play` is the remedy both warnings name, so it has
  to be able to fix a root-owned file rather than only re-observe the EPERM.
  The two near-duplicate blocks collapsed into one loop.
- Both Ansible pre-chowns became `<user>:<user>`.

Verified live, both directions, on the running pod:

```
before fix   rotate db  →  WARNING: could not chown .../exporter.my.cnf to the
                           exporter uid inside the userns …
                           file left 1001:0 (carlos:root)
after fix    rotate db  →  no warning; file 231069:231069  (== container 65534:65534)
             play path  →  root:root file repaired to 231069:231069 in one pass
```

Tests: 5 unit pins (the helper sets a real gid and never raises; the
provisioning hand-over precedes the userns chown; `play` repairs before it
maps) and 1 static Ansible-checks pin that fails on any bare
`chown "{{ carlos_service_user }}"` feeding a `podman unshare chown`.
Mutation-checked: restoring `-1` fails the unit pin, restoring the bare
`chown <user>` fails the Ansible pin.

### M1 (MEDIUM, data handling). `db-backup` silently dropped every argument after the first, and `carlos-ctl db-backup --help` took a plaintext-PHI snapshot into a directory named `--help`. **Fixed.**

`cmd_db_backup` read `args[0]` and ignored the rest, and its name regex
`[A-Za-z0-9._-]+` accepts a leading dash. Verified live:

```
$ carlos-ctl db-backup --help
[00] 2026-08-02 17:29:24 completed OK!
==> Snapshot ready: /usr/local/emr/backup/mariadb-hot/--help
$ carlos-ctl db-backup x y      # silently snapshotted 'x', dropped 'y'
```

So an operator reaching for usage on the one verb that writes a **full
plaintext copy of the live datadir** got the copy instead — into a directory
whose name needs `rm -rf -- --help` to remove — and any mistyped flag
(`db-backup nightly --compress`) was silently discarded. This is exactly the
class `cli.py`'s no-argument-verb guard exists to prevent: *"silently-ignored
flags on destructive verbs are how operators get the opposite of what they
asked for."* `db-backup` was the one verb taking a positional that had no
argument-count check at all (`logs`, `pma`, `instances`, `rotate`, `secrets`
and `backup` all validate).

**Fix.** Reject more than one argument, and reject a leading `-`, both
**before** the credential lookup and the snapshot — so a refused invocation
writes nothing. A plain name still works unchanged.

```
$ carlos-ctl db-backup --help
ERROR: usage: carlos-ctl db-backup [name]  — '--help' looks like a flag, and this
verb has none; a name may not start with '-' (it becomes a directory under
/usr/local/emr/backup/mariadb-hot)
$ carlos-ctl db-backup nightly --compress
ERROR: usage: carlos-ctl db-backup [name]  — one optional name, got 2 arguments
(nightly --compress); this verb has no flags
```

Tests: 5 unit pins (extra args, long/short flag shapes, no snapshot attempted
before the refusal, a plain name still accepted) and 4 e2e pins driving the
real CLI. Mutation-checked: neutering either guard fails three of the unit
pins.

## Not findings (checked, behaved correctly)

- **`backup restore` on an unknown argument** aborts (`warn` + `return False`)
  rather than proceeding with a silently-ignored `--stop-datetime` — checked
  because a dropped stop-instant would replay the very event a PITR is trying
  to escape.
- **`restic.env` readability by the rootless restic container.** A hand-made
  root:root env file makes every `carlos-ctl backup` verb die at
  `podman run --env-file` with `permission denied` (surfacing as
  `ERROR: restic init failed`, which points at the repository, not the file).
  The Ansible role's subuid-aware ownership sweep covers
  `{{ carlos_conf_dir }}/restic`, so a real provisioned install is fine; this
  was a sandbox artifact of laying out `$EMR_HOME` by hand.
- **`uninstall` removing `container/guard/`** — deliberate (the go-live marker
  dir), documented in the code; the playbook recreates it, and a `kube play`
  of the rendered spec before re-provisioning fails loudly on the missing
  hostPath rather than silently.
- **`util.shell_unquote_value`** round-trips every `bash printf %q` form
  tested (17 samples incl. multibyte, control chars, backslashes, quotes);
  `size_to_mib` handles decimal/k8s/JVM units and rejects junk.
- **`tlsops._chown_service_user`** also passes `-1` for the gid, but nothing
  downstream hands those files to a userns chown and their modes are
  0640/0644 read by container-root — left as is.

## Environment notes (not defects in this repo)

- No systemd as PID 1 in the sandbox, so every `systemctl` path degraded
  loudly and correctly: `seal`/`rotate db` ended rc 1 on the
  `carlos-secrets.service` daemon-reload (the seal itself completed and said
  so), `enable` listed all six timers it could not enable, and `play`/`down`
  took their documented non-systemd `kube play`/`pod stop` fallbacks.
- `/dev/net/tun` ships mode 0600 in this image; rootless `slirp4netns` needs
  it, so the first build failed at the network setup step. The `finally` in
  `cmd_build` still restored `.extra-ca-bundle.crt` to its 0-byte placeholder.
- `nofile` hard limit is capped at 4096 and cannot be raised, which is exactly
  the verified floor the forked-javac Containerfile targets — the build passed
  with `--ulimit nofile=4096:4096`, and `cmd_build` correctly did not warn.
