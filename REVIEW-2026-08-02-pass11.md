## New findings

### H1 (HIGH, backup/PITR). The binlog chain-pollution defense has never been active on ANY CARLOS deployment: the identity probe asks for a MySQL-only variable. **Fixed.**

`carlos_ctl/backup.py:server_identity()` resolved the datadir lineage id with

```sql
SELECT @@server_uuid
```

`server_uuid` is a **MySQL** system variable. MariaDB does not have it — and
MariaDB is what this deployment pins (`DB_IMAGE = mariadb:11.4.12`). Measured
live against the running pod, through the CLI's own code path:

```
rc = 1
stderr = "ERROR 1193 (HY000) at line 1: Unknown system variable 'server_uuid'"
server_identity() = ''
```

Every consumer short-circuits on an empty identity, so **all four** layers of
the chain-pollution defense were inert:

| Consumer | Guard | State before the fix |
|---|---|---|
| `ship_binlogs` | refuse to ship a rebuilt server's binlogs over an existing chain | never evaluated |
| `ship_binlogs` | write `.carlos-server-identity` into the snapshot | never written (confirmed absent from `restic ls latest --tag binlog`) |
| `_full_backup` | write `-- carlos-server-uuid:` as the dump's first line | never written (confirmed absent from `restic dump latest --tag db`) |
| `_verify_restore` / `_restore_pitr` | FAIL / REFUSE on a dump-vs-chain identity mismatch | never evaluated |

The only visible symptom was a warning that **misattributed the cause** —
`binlog chain identity UNVERIFIED (pre-identity dump/snapshots)` — which reads
as "your old snapshots predate the feature" and ages out of an operator's
attention, on a repository whose snapshots were *all* created by the current
code. This is the guard that stops a rebuilt/DR host's unrelated
`binlog.000001+` masking the real chain (replay then either refuses a
recoverable dump as "anchor pruned", losing up to a day of committed clinical
writes, or — on a sequence collision — applies another server's events as
corruption).

Fix: keep `@@server_uuid` for MySQL-flavored servers, and fall back to a
uuid4 **minted into a dotfile at the datadir root**
(`<data>/mariadb-mnt/.carlos-server-identity`, 0644). That gives exactly the
lineage semantics the docstring always described: a physical datadir
backup/restore carries it, a freshly-initialized datadir has none. Minting is
gated on `datadir_initialized()` so an unmounted mountpoint is never handed a
fabricated lineage. Both UNVERIFIED messages now name **which side** lacks an
id and stop implying "legacy data".

Verified live, after the fix:

```
==> minted this datadir's binlog-chain lineage id (.carlos-server-identity)
$ cat /opt/emr/data/mariadb-mnt/.carlos-server-identity
17edfc5c-37e5-4a9a-a343-b5c08a8b0d5e
$ ls /opt/emr/data/mariadb-binlog/.carlos-server-identity   # sidecar now shipped
$ carlos-ctl backup verify        # no UNVERIFIED warning — chain identity checked
==> Restore drill OK
```

and the guard itself proven to fire, by simulating a rebuilt server:

```
$ printf '%s\n' "$(uuidgen)" > /opt/emr/data/mariadb-mnt/.carlos-server-identity
$ carlos-ctl backup binlogs
WARNING: this server's identity (9247c63c-…) differs from the identity that
last shipped into this repository (17edfc5c-…) — a rebuilt/DR server's
unrelated binlogs must not pollute the existing PITR chain …
rc=1
$ CARLOS_ACCEPT_NEW_BINLOG_IDENTITY=1 carlos-ctl backup binlogs   # documented override
==> Backup (binlogs) complete
```

Pins: `tests/unit/test_backup.py::TestServerIdentity` (4 cases, including
"an uninitialized datadir mints nothing").

### H2 (HIGH, credentials). A DB password containing `#{` or `${` is boot-fatal for the app and leaks a fragment of itself into the application log. **Fixed.**

Found by deploying with a deliberately hostile password,
`dev@P4ss & "w\rd#{ok}` — every character of which the repo's own hermetic
suite advertises as supported ("dev-setup renders with a `@ \ & "` password
(charset-agnostic)"). The pod came up, MariaDB accepted the credential, and
`/carlos/` served **404 for ten minutes**. The cause:

```
ERROR context.ContextLoader - Context initialization failed
… BeanExpressionException: Expression parsing failed
… SpelEvaluationException: EL1008E: Property or field 'ok' cannot be found
   on object of type 'BeanExpressionContext'
```

`spring_jpa.xml` reads the password as
`<property name="password" value="${db_password}" />`. Spring resolves the
placeholder **and then runs the resulting VALUE through the
BeanExpressionResolver**, so a `#{…}` inside the password is evaluated as
SpEL. Two consequences, both bad:

1. **Boot-fatal, with no diagnosis pointing at the password.** The whole
   webapp context fails; the operator sees a Spring bean error naming an
   identifier they never wrote.
2. **Credential leakage into the application log.** The error text is
   `Property or field 'ok' cannot be found` — `ok` being the literal body of
   the `#{ok}` in the password. A fragment of a live DB credential is written
   to the app log (and, in a production topology, shipped into the 180-day
   VictoriaLogs store).

`${` is the same class one layer earlier: it is re-resolved as a nested
placeholder, so the app silently authenticates with a **different string**
than the one provisioned. Neither is escapable — `.properties` has no escape
that survives Spring's second pass.

Fix: refuse `${` and `#{` in `validate_db_password()` (which covers `setup`,
`db-users`, `rotate db`, `rotate db-root`, and every
`CARLOS_DB_*_PASSWORD` override) and in `scripts/dev-setup.sh`, with a message
that names the cause. A bare `$` or `#` stays legal. Verified live: all three
entry points now refuse, and the previously-hostile-minus-SpEL password
(`dev@P4ss & "w\rd`) still renders and boots.

Pins: `tests/unit/test_secrets.py::TestValidateDbPassword` (3 new cases).

### M1 (MEDIUM, operability). `carlos-ctl monitor` printed NOTHING about what it found. **Fixed.**

The CLI usage advertises `monitor` as an operator verb ("run the health
checks now"), but `MonitorRun.alert()` dispatched every finding to journald
and the alert channel only. A hand-run sweep produced **zero terminal output**
and exited 1 — measured live: five real faults relayed to the webhook, an
empty terminal. `check`, by contrast, prints every `ok`/`FAIL`. On a host
being triaged (or one whose journald is not being read) the operator had to
go find the journal to learn what their own command had just discovered.

Fix: print `FAIL <finding>` to stderr for every alert, throttled or not,
alongside the existing dispatch. Timer runs are unaffected — systemd captures
stderr into the same journal the `logger` call already writes to. Verified
live:

```
$ carlos-ctl monitor
FAIL TLS certificate file …/fullchain.pem is MISSING on a deployed instance …
FAIL container not running: carlos-app-drugref
FAIL NOTHING serves the front door https://127.0.0.1:443/ …
… rc=1
```

Pins: `tests/unit/test_monitor.py::TestFindingsReachTheOperator`.

### M2 (MEDIUM, deploy). A configured-but-never-executed healthcheck made `play` burn the full readiness budget and then fail a healthy stack. **Fixed.**

`_wait_container_healthy` has two paths: `healthy` → pass, and *no healthcheck
configured* → exec the pod spec's own probe (finding S15). A third shape
exists and was measured live here: the healthcheck **is** configured but
podman never runs it, because podman drives healthchecks from transient
systemd timers.

```
$ podman inspect carlos-app-db --format '{{json .State.Health}}'
{"Status":"starting","FailingStreak":0,"Log":null}      # 11 minutes in
```

Status is `starting` (not empty), so the fallback never engages; the gate
polls to the per-container deadline (1320 s for db/carlos) and returns False.
Reproduced through the CLI's own code:

```
wait_container_healthy(db) -> False (deadline reached)
fallback probe rc = 0          # the container's OWN declared probe passes
carlos fallback probe rc = 0
```

`play` would report "the app is not serving, NO markers written, NO timers
armed" about a stack that was serving fine — and would do so 22 minutes late.
The README does require systemd ≥ 248, so this is a degraded-host hardening
rather than a mainline break; but it is the shape a broken user manager
produces, and the failure message points at the app.

Fix: when the status is `starting`, a fallback probe exists, and
`.State.Health.Log` is still empty after `_NEVER_RAN_GRACE` (180 s, above the
specs' longest startPeriod+interval), exec the declared probe — the same
fail-closed command the no-healthcheck path uses, with a warning naming the
real cause. A **slow** app produces failing log entries, so it stays on the
normal polling path; nothing greens without a passing probe.

Pins: `tests/unit/test_lifecycle.py::TestHealthcheckNeverRuns` (3 cases,
including "a check that HAS run keeps normal polling").

### M3 (MEDIUM, configuration). `CARLOS_EXTRA_CA_BUNDLE` and `CARLOS_BUILD_DIR` were silently ignored in the documented configuration file. **Fixed.**

Both were read with `settings._env.get(...)` — the **process environment
only**. But `carlos-app.env` is the documented configuration surface: the CLI
usage says "Configuration comes from `$EMR_HOME/container/carlos-app.env` …
environment variables provide defaults for anything unset there", which is
exactly backwards for these two. Setting `CARLOS_EXTRA_CA_BUNDLE` there — the
natural place, and where an Ansible `carlos_extra_env` line writes it — both
warned that carlos-ctl "does not read" the key *and* did nothing. Measured
live:

```
# (a) value in carlos-app.env, pointing at an unreadable path
WARNING: … carries key(s) carlos-ctl does not read: CARLOS_BUILD_DIR, CARLOS_EXTRA_CA_BUNDLE
==> Building localhost/carlos-app:build-…              # proceeded, CA NOT staged

# (b) same value in the process env
ERROR: CARLOS_EXTRA_CA_BUNDLE=/definitely/not/here.pem is not readable …
```

On the host class the knob exists for — a hospital/corporate TLS-inspecting
egress proxy — path (a) means the CA is never staged and the build dies on a
bare Maven PKIX error roughly twenty minutes in, with the operator's
configuration apparently in place.

Fix: register both in `config._EXTRA_KNOWN_KEYS` and read them through
`Settings.get` (env file wins over process env, like every other knob).
Neither is a secret — both are paths. Verified live with the process env
explicitly unset: the CA was staged from the env-file value and the unknown-key
warning is gone.

Pins: `tests/unit/test_build.py::TestBuildContextKnobs`.

### L1 (LOW, recovery docs). `db-backup` and the README point a recovering operator at a file that does not exist. **Fixed.**

`carlos-ctl db-backup` prints "binlog coordinates in `xtrabackup_binlog_info`",
and README "Native MariaDB physical backups" says the same. MariaDB's
`mariadb-backup` renamed the metadata files; the pinned `mariadb:11.4.12`
writes only the `mariadb_backup_*` names. Confirmed on a real snapshot taken
during this pass:

```
mariadb_backup_binlog_info      <- the binlog coordinates (binlog.000003  12365  0-1-1854)
mariadb_backup_checkpoints
mariadb_backup_info
xtrabackup_binlog_pos_innodb    <- InnoDB LSN positions, NOT what a PITR needs
```

Note the near-miss: `xtrabackup_binlog_pos_innodb` **is** still written, so an
operator following the message finds a plausibly-named file with the wrong
contents. Both strings corrected, with the distinction spelled out.

### L2 (LOW, images). Both Containerfiles' `HEALTHCHECK` was silently dropped from every image built. **Fixed.**

`podman build` defaults to the OCI image format, which has no healthcheck
field, so podman discards the directive with a warning buried in thousands of
build-log lines:

```
level=warning msg="HEALTHCHECK is not supported for OCI image format and will be ignored.
Must use `docker` format"        (x6 across the two images)
```

The shipped images carried none — verified by running the real
`localhost/carlos-app:latest` and inspecting the container:
`Config.Healthcheck = null`. Under `kube play` the pod spec's own probes
govern, so nothing was broken in the deployed topology; but the Containerfile
carries a deliberate, commented HTTP-status HEALTHCHECK ("Liveness for a
STANDALONE `podman run`… a deadlocked or failed-deploy webapp keeps the socket
accepting while serving nothing — that must read unhealthy"), and that is
exactly the case an operator debugging a bad build reaches for. It never
existed.

Fix: `carlos-ctl build` now passes `--format docker` for both images.
Verified live with a control (a two-line Containerfile built both ways) and
then on the real images after a rebuild:

```
localhost/carlos-app:latest   -> {"Test":["CMD-SHELL","bash -c 'exec 3<>/dev/tcp/127.0.0.1/8080 …
localhost/carlos-drugref:latest -> {"Test":["CMD-SHELL","bash -c 'exec 3<>/dev/tcp/127.0.0.1/8180 …
```

and the six OCI warnings are gone from the build log.

### L3 (LOW, build time). The image build compiles 1118 test sources it never ships. **Reported, not changed.**

The Containerfile builds with `mvn -B -DskipTests=true … package`, which skips
test *execution* but not test *compilation*. Both full builds in this pass
logged:

```
[INFO] Compiling 4078 source files with javac … to target/classes
[INFO] Compiling 1118 source files with javac … to target/test-classes
```

`target/test-classes` is not packaged into the WAR, so this is pure cost —
wall-clock and, more relevantly for this repo, file-descriptor and memory
pressure inside a build with a documented history of dying at exactly 4096
`nofile`. `-Dmaven.test.skip=true` skips both. Left unchanged deliberately:
the change is a one-token swap but verifying it properly means another full
build **and** a deploy + Playwright pass to prove the WAR is byte-equivalent
in behavior, and this pass's budget went to the correctness findings above.
Worth doing as its own change.

### I1 (INFORMATIONAL, cross-repo). The app repo's Playwright suite mis-parses a backslash-bearing DB password. **Documented in QUICKSTART; fix belongs in `carlos-emr/carlos`.**

`scripts/login-playwright-checks.js` writes

```js
fs.writeFileSync(file, `[client]\npassword=${mysqlPassword}\n`, { mode: 0o600 });
```

into a MariaDB `--defaults-extra-file`, where a backslash is an escape. With
the password `dev@P4ss & "w\rd` — which `dev-setup.sh` accepts and the
hermetic suite explicitly covers — every DB call in the suite failed with
`ERROR 1045 … Access denied`, before a single browser check ran. This is the
same defect class carlos-podman already fixed on its own side with
`properties_escape_value`; the suite needs the same treatment (or should pass
the password via `MYSQL_PWD`).

Worked around for this pass by exporting the value with doubled backslashes,
after which the suite passed **14/14**. QUICKSTART now documents the
workaround, and — because the identical trap bit this review's own
hand-written `SET PASSWORD` (a `\r` in the SQL literal silently set a
CR-bearing credential) — also points at `carlos_ctl.util.sql_escape` for
scripted password changes.
