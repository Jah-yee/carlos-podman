# carlos-podman — eighteenth-pass review + live end-to-end test report (2026-08-03)

Scope: a fresh review of `carlos_ctl/`, the Ansible role and the gate suites,
plus a **live end-to-end exercise of the FULL production topology** on a
clean host: `ansible/site.yml` run for real against a bare machine (no
service account, no `$EMR_HOME`), both images built from source
(`carlos-emr/carlos@develop`, `drugref2026@master`), all three pods started
through `carlos-ctl play`, the Ontario Flyway schema, the DrugRef database,
the app repo's Playwright login suite, every backup tier including the
point-in-time restore drill, and a systematic drive of the **complete**
`carlos-ctl` verb matrix. Everything reported fixed through
`REVIEW-2026-08-03-pass17.md` was treated as baseline; only NEW findings are
reported here.

Environment: podman **4.9.3** (the documented floor), Ubuntu 24.04, no
systemd PID 1, cgroup v1, TLS-intercepting CONNECT-only egress proxy,
`nofile` hard cap 4096.

## Why this pass found a deploy-blocker seventeen passes missed

**H1 is host-conditional, which is exactly why it stayed hidden.** podman's
rootless network namespace masks the CNI *state* directory by walking UP from
`/var/lib/cni` to the first path that exists. On a host where that directory
exists, it masks only that — harmless. On a host where it does not, the walk
lands on **`/var/lib`** — and the role put the service user's home, hence
podman's graphroot and netavark's network definitions, right under it. Nothing
creates `/var/lib/cni` on a netavark-only host, so a plain
`apt install podman` on Ubuntu 24.04 lands in the broken half.

Which half a sandbox falls into is invisible unless you look, so seventeen
passes on a host that happened to have `/var/lib/cni` saw nothing. This pass
also started from a genuinely bare machine, so the role's own
`ansible.builtin.user` task created the account — and chose its home — for the
first time.

The other three findings come from paths that are documented but were never
driven end to end: the recovery half of the documented maintenance runbook
(**H2**), the DrugRef remedy added by pass 17 itself (**H3**), and the gate
suite's own isolation from a developer's provisioned checkout (**M1**).

## New findings

### H1 (HIGH, deploy-blocking on a netavark-only host): the service user's home is hidden inside podman's own rootless network namespace, so no pod can start

`tasks/host.yml` created the rootless engine owner with

```yaml
home: "/var/lib/{{ carlos_service_user }}"
```

the canonical home for a system account. podman's **rootless network
namespace** bind-mounts an empty scratch dir over the CNI state directory —
and `libpod/networking_linux.go` (v4.9.3) walks UP from `/var/lib/cni` to the
first path that exists:

```go
persistentCNIDir = "/var/lib/cni"
...
// we can only mount to a target dir which exists, check /var/lib/cni recursively
for {
    if _, err := os.Stat(varTarget); err == nil { varDir = r.getPath(varTarget); break }
    varTarget = filepath.Dir(varTarget)      // /var/lib/cni -> /var/lib -> /var
    ...
}
err = unix.Mount(varDir, varTarget, "none", unix.MS_BIND, "")
```

Nothing creates `/var/lib/cni` on a netavark-only host — the
`containernetworking-plugins` package ships binaries to `/usr/lib/cni` and the
*state* dir is made lazily by CNI itself — so the walk lands on **`/var/lib`**
and masks all of it.

**Version scope** (checked against the sources, not assumed): in podman 4.x
this block is **unconditional** — it runs whatever the network backend is, so
netavark installs get `/var/lib` masked. In podman 5 the same code moved to
`containers/common`
(`libnetwork/internal/rootlessnetns/netns_linux.go`) and is now **gated on
`n.backend == CNI`**, so a netavark install is unaffected. podman 4.9 is this
project's documented floor and what RHEL 9 / Ubuntu 24.04 / Debian 12 ship, so
the hazard is live for the primary targets today and disappears on podman 5.
The `/run` mask (step 5) is unconditional in **both**. The service user's podman graphroot is
`$HOME/.local/share/containers/storage` and netavark reads its network
definitions from `<graphroot>/networks`, so with a `/var/lib/<user>` home
those definitions are **invisible inside the very namespace that has to
resolve them**.

Every pod here is on a named bridge network, so `carlos-ctl play` dies on its
first `podman kube play`:

```
Successfully loaded 4 networks          <- parent
Successfully loaded 1 networks          <- inside the rootless netns
Error: unable to find network with name or ID carlos-net: network not found
ERROR: kube play failed for .../carlos-obs.yaml — deploy aborted
```

The message points at the network, which is the one thing that is fine:
`podman network ls` and `podman network inspect carlos-net` both succeed on
the host.

**Clean-room A/B**, two pristine service accounts created for the test — own
65536 subuid/subgid ranges, own tmpfs `XDG_RUNTIME_DIR`, no prior podman
state — differing ONLY in home location:

```
atest  home=/var/opt/atest   podman run --network pnet  ->  RESULT_OK
btest  home=/var/lib/btest   podman run --network pnet  ->  network not found
```

with `podman network ls` listing `pnet` for both, and the masking visible
side by side:

```
btest  host view : netavark.lock pnet.json      atest  host view : netavark.lock pnet.json
btest  netns view: netavark.lock                atest  netns view: netavark.lock pnet.json
```

The source predicts a falsifiable test, and it holds: `mkdir /var/lib/cni`
moves the mask from `/var/lib` down to `/var/lib/cni`, and btest goes to
`RESULT_OK` on the next run with nothing else changed.

A fresh install on an affected host therefore never comes up: no `.deployed`
marker, no timers, no backups, no monitoring. `rebuild` and `rollback`, which
trust play's exit code, inherit it.

**Fixed with the smallest thing that actually removes the hazard**: the role
ensures `/var/lib/cni` exists. That is the entire fix — no relocation, no
downtime, no engine-store move. Verified live by restoring the broken state on
the deployed host (remove the directory, move the account back to
`/var/lib/carlos`, reproduce "network not found"), then re-running the
playbook: it left the home untouched, created the directory, bridge networking
came back, and the full 15-container stack played green (`play` 0 twice in a
row, `check` 42/3).

Belt and braces on top of that:

- `carlos_service_user_home`, default `/var/opt/<user>` — outside both masked
  prefixes, always on local disk, and (unlike `/home/<user>`, which most
  rootless-podman guides use) never on an NFS/autofs mount, where overlayfs
  does not work and podman silently falls back to the `vfs` driver.
- An assert refusing an explicit home under `/run`/`/var/run` — the one prefix
  with **no** escape hatch, since podman replaces `/run` unconditionally in
  every version and it is tmpfs anyway. `/var/lib` is deliberately **not**
  refused: with the state dir present it works, and a blanket refusal would
  reject the FHS-canonical layout for no reason.
- A `play`-time preflight that asks podman for the **live graphroot**
  (`podman info`) rather than deriving it from the home, and checks the real
  condition (store under the masked parent AND the state dir absent). A
  site-supplied `storage.conf` (`rootless_storage_path`) can move the store,
  and then the home says nothing about where the hazard applies.
- A guard refusing to silently relocate an existing account's home:
  `ansible.builtin.user` rewrites `/etc/passwd` but does not move the
  directory, so changing the variable on a provisioned host would repoint
  podman at an empty graphroot and orphan the image store — and the podman
  secret store with it, whose file driver records ABSOLUTE paths in
  `secrets.json` that nothing relocates (`podman secret rm` then fails with
  `mkdir <old home>: permission denied`, so it cannot even be repaired by
  recreating). Deliberately NOT automated: moving a live engine store needs
  the instance stopped, and that is the operator's call. The refusal carries
  the recipe.

### H2 (HIGH): `carlos-ctl enable` reports failure on every default install, and its verdict is false

`cmd_enable` enabled a hardcoded timer list:

```python
for t in ("backup", "binlog", "docs", "backup-verify", "monitor", "cert-renew"):
```

The cert-renew timer is rendered **only in acme mode** — `cleanup.yml`
removes it in the other two — so on the DEFAULT `selfsigned` mode
`systemctl enable <instance>-cert-renew.timer` always fails, and `enable`
returns 1 with:

```
WARNING: enable did NOT fully apply — failed: carlos-cert-renew.timer.
The masked units/timers stay off (the EMR will NOT start at the next boot);
fix the systemd user manager for 'carlos' and re-run
```

Every word after the semicolon is wrong: the pod units had just been unmasked
correctly and the systemd user manager is fine. `enable` is step 2's stated
reverse in the README's own "Patching & rebooting the host" runbook
(`down --disable` → patch → reboot → `play`/`enable`), so an operator
finishing planned maintenance on a PHI system is told the EMR will not come
back — and the nonzero rc breaks `carlos-ctl enable && …` scripting.
`start_instance_timers` already mode-gates the same list, with a comment
saying exactly why; the gate had simply never been applied here.

Fixed by mirroring `start_instance_timers`: mode-gate cert-renew, and treat a
timer whose unit file is absent as its own warning (naming the playbook)
rather than as evidence that systemd is broken. Only a REAL `systemctl`
failure still counts toward the "did not fully apply" verdict. Verified live
on the deployed instance — `down --disable` → `enable` → `play` → `status`
now returns 0 at every step — and pinned by five unit tests (selfsigned
clean; acme still enables cert-renew; an uninstalled timer warns without the
false verdict; an installed timer that systemctl refuses still fails; a
failed unmask still fails).

### H3 (HIGH): the `==> target:` banner rides STDOUT, so the README's own DrugRef remedy corrupts its own pipeline

`_target_banner` printed to stdout. `db` carries the banner because imports
touch data — and `db` is also the documented **scripting** idiom. The banner
therefore became the first line of every captured or piped result, so pass
17's own M1 remedy, the one that stops every nightly backup from refusing:

```bash
sudo carlos-ctl db -N -B -e "SELECT CONCAT('ALTER TABLE …')" | sudo carlos-ctl db drugref2
```

fed `==> target: instance=carlos …` to mariadb. Run verbatim on the live
instance:

```
ERROR 1064 (42000) at line 1: You have an error in your SQL syntax; …
near '==> target: instance=carlos  EMR_HOME=/home/carlos/emr  env=/home/carlos/…' at line 1
```

All 17 `drugref2` tables stayed `ENGINE=Aria` — which is exactly the state
that makes `backup full` refuse the nightly dump and `backup verify` fail
with it. The failure reads as a MariaDB syntax error, so an operator has no
reason to suspect the CLI, and the backups stay broken.

Fixed by printing the banner to **stderr**, which is where operator context
belongs: the wrong-instance guard still shows on a terminal, and the data
stream is clean. (`db-dump` already gets no banner for the same reason —
this was the gap in that intent.) Verified by running the README recipe
verbatim afterwards: all 17 tables converted, `oscar.formRourke2009` correctly
left as the one known-unconvertible Aria table, `backup full` and
`backup verify` both green. Pinned by two unit tests.

### M1 (MEDIUM): `tests/ansible-checks.sh` is not hermetic against the repo's own gitignored `host_vars`

The suite `cd`s to `$ROOT/ansible` and runs `site.yml` there. Ansible
auto-loads `host_vars/` next to the playbook, and `ansible/host_vars/<instance>.yml`
is exactly what `carlos-ctl setup` writes (and what `.gitignore` explicitly
anticipates). With the default instance name that file is `host_vars/carlos.yml`,
and every scenario host in the suite is named `carlos` — so a developer's own
site configuration was silently injected into all twelve `--check` gates.

Measured, holding everything else constant:

```
without ansible/host_vars/carlos.yml : playbook rc=2, assert fires  -> gate PASSES
with    ansible/host_vars/carlos.yml : playbook rc=0               -> "FAIL: acme mode
                                        with the placeholder SERVER_NAME was NOT refused"
```

A local `carlos_server_name` was enough to flip a real safety gate. The
false-fail direction is merely confusing; the **masking** direction is the
dangerous one — a local value that happens to satisfy a scenario turns a
genuinely broken assert green, and the suite is the only thing pinning
several deploy-blockers found in earlier passes.

Fixed by running every `--check` scenario against a copy of the play in the
throwaway work directory, with the checkout's top-level entries (except
`ansible/`) mirrored beside it so the role's `{{ playbook_dir }}/../…`
lookups still resolve. Confirmed: the full suite is green with a provisioned
`ansible/host_vars/carlos.yml` present.

## A correction worth recording

H1 was first written up as unconditional — "a `/var/lib` home always breaks
podman bridge networking" — and the first fix relocated the service account's
home to `/var/opt/<user>` with `move_home`, dragging a multi-gigabyte engine
store and a podman secret-store path rewrite with it. That framing was wrong
in a way worth recording, because the correct mechanism only turned up when
the claim was pressed against seventeen green prior passes:

- the mask is **conditional** on `/var/lib/cni` being absent, and podman's own
  source says so ("if /var/lib/cni does not exist, use the parent dir"). A
  host that has it is unaffected — which is the most likely reason earlier
  passes saw nothing;
- so the proportionate fix is an **empty directory**, not a home relocation.
  Forcing every existing install through a home move — with the instance
  stopped, on a PHI system, to fix something a `mkdir` fixes — would have been
  a far bigger risk than the bug.

The relocation machinery was then removed outright: with **no existing
installs** (carlos-podman is pre-release), it was ~100 lines serving a case
that does not exist — `move_home`, two `usermod` pre-check probes, and a
podman secret-store path rewrite, none of which a fresh install ever
executes. What replaced it is one assert that REFUSES to silently relocate an
existing account's home and hands the operator the recipe. Dead migration code
is worse than none: it is untested-in-practice complexity a future maintainer
has to reason about.

Method note for the next pass: the original A/B was run on a sandbox whose
podman state this review had already disturbed (podman invoked without
`XDG_RUNTIME_DIR`, `/run/user/<uid>` remounted mid-flight, the libpod db
deleted). That is not evidence. The A/B that counts was re-run afterwards on
two accounts created for the purpose, with their own subid ranges and runtime
dirs and no prior podman state — and then confirmed by a prediction derived
from the source (`mkdir /var/lib/cni` flips the broken account to working).

- **Leaked aardvark DNS entries after a FORCE removal**: chasing a
  `check` failure ("waf cannot reach carlos-app:8443") showed aardvark
  returning a stale A record beside the live one; `/dev/tcp` tries the dead
  address first and stalls ~5 s, overshooting the probe's 5 s timeout — so the
  check's verdict was true but its remedy text ("point BACKEND at the
  container name") would have been the wrong action. The stale entries traced
  to infra containers this review had force-removed
  (`podman pod rm -f` plus SIGKILLed processes); a CLEAN `down` + `play` cycle
  removed its own entries correctly, leaving only the force-removed ones. Not
  a defect in this repo — recorded because the misleading remedy text is worth
  knowing, and because a `check` run immediately after `play` can also trip
  this probe before DNS settles.

## Environment notes (not defects in this repo)

- **No systemd PID 1.** `loginctl` and `systemctl` were shimmed to the minimum
  the role and CLI need (linger marker, unit-file-aware `enable`/`disable`,
  no-op activation). Unit ACTIVATION is therefore not verified here; the
  quadlet branch of `play` was bypassed and the documented `podman kube play`
  fallback exercised instead.
- podman drives healthchecks from transient systemd timers, so none ran on
  their own. The `_NEVER_RAN_GRACE` fallback was exercised first; afterwards
  `podman healthcheck run` was invoked on a loop to stand in for the timers.
- **cgroup v1**: rootless resource limits are silently unenforced (podman says
  so per container); the pod specs' limits are ignored here.
- `/run/user/<uid>` had to be a real tmpfs (systemd-logind normally mounts it)
  — podman's rootless netns requires it.
- The egress proxy serves CONNECT only, so a local HTTP→HTTPS upgrading
  forward proxy was placed in front of it for `apt` inside the image builds,
  and a `mysql` shim forwarded the Playwright suite's queries through
  `podman exec` rather than weakening the deployment's no-TCP-port DB
  isolation. Nothing in this repo is involved in either.
