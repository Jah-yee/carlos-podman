## New findings

### H1 (HIGH, backup/verify). The weekly restore drill's readiness gate is satisfied by MariaDB's *initialization* server, so the drill fails on every run — with a diagnosis that names the wrong knob. **Fixed.**

`carlos_ctl/backup.py:_verify_restore`. The gate was a bare
`mariadb-admin --user=root ping` over the container's **unix socket**. The
official mariadb image initializes an empty datadir by starting a
**temporary server on that same socket**, running the init SQL, shutting it
down, and only then exec'ing the real server. The socket ping is satisfied
by that temp server, so the drill broke out of its wait, walked into the
shutdown gap, and failed the dump load with a raw
`ERROR 2002 (HY000): Can't connect to local server through socket
'/run/mysqld/mysqld.sock' (2)` — surfaced under the
`could not load carlos-databases.sql ... raise VERIFY_TMPFS_SIZE` message,
which sends the operator at a tmpfs-sizing fix for a readiness bug.

**Measured live** (`mariadb:11.4.12`, tight poll, idle host):

| t | socket `ping` | `--protocol=tcp` ping | `healthcheck.sh --connect` |
|---|---|---|---|
| 3.6 s | **OK (false ready)** | fail | fail |
| 4.5–5.8 s | fail (socket gone) | fail | fail |
| ≥ 6.5 s | OK | OK | OK |

This is **deterministic, not load-dependent** — pass-9 recorded it as a
"container-startup race under heavy sandbox load" and pass-8/pass-9 added
exhaustion and container-`running` guards, but neither can catch it: the
container is `running` throughout, because the temp server is a child of the
entrypoint script, not PID 1. It reproduced on the **first** drill run here
and again on a second, on an otherwise-idle host.

Impact: `carlos-ctl backup verify` is the only end-to-end proof that a PHI
system's backups actually restore. On any host whose scratch server takes
the normal init path, that proof never runs, and the weekly alert points at
the wrong cause.

Fix: gate on the image's own healthcheck, falling back to a **TCP** ping —
the temp server runs `--skip-networking`, so neither can be satisfied by it.
This is the same gate the pod specs' db `readinessProbe` already uses.
After the fix the drill completed end to end: dump loaded, 3 binlogs
replayed, core-table row counts reported, `Restore drill OK`. Pin:
`TestVerifyDrillServer::test_readiness_gate_is_not_a_bare_socket_ping`.

### M1 (MEDIUM, dev path). `carlos-ctl seal` on a QUICKSTART instance bricks the next `kube play`. **Documented in the spec.**

`examples/carlos-app-dev.yaml` mounts its `app-secrets` volume from
`$EMR_HOME/run/app-secrets`, but `Settings.run_secrets_dir` — where `seal`,
`secrets render` and every `rotate` write the unsealed fragments — defaults
to `/run/<instance>-emr` (the production `carlos_run_secrets_dir`). Sealing
a dev instance therefore rewrites the base `carlos.properties` to
`db_password=__SEALED__` while the real fragment lands somewhere the dev pod
never mounts, and the spec's own `carlos-init` guard then hard-fails the
deploy with `FATAL: db_password is __SEALED__ with no unsealed fragment`.
Hit live: the app came back only after the fragments were copied to the path
the spec mounts. `seal` is a documented verb and the dev spec carries the
`app-secrets` mount and the `__SEALED__` check, so the two are meant to work
together. Fixed by documenting the divergence and the
`CARLOS_RUN_SECRETS_DIR=$EMR_HOME/run/app-secrets` override at the volume
definition, rather than moving a path that `dev-setup.sh` creates without
root.

### L1 (LOW, tests). `tests/ansible-checks.sh`'s own install hint omits the `bcrypt<4.1` pin it requires. **Fixed.**

The skip message printed when `ansible-playbook` is absent says
`pip install ansible-core passlib netaddr` — which today pulls bcrypt 5.x,
the exact combination the role's G1 gate rejects. Following the hint
guarantees a failed run. (README and `.github/workflows/tests.yml` both carry
the pin; only this hint did not.) Worth noting for the gate's own message
text: on bcrypt 5.x the underlying error is
`password cannot be longer than 72 bytes` — passlib 1.7.4's backend self-test
uses an over-72-byte secret — not the `__about__` AttributeError the rescue
message describes. The prescribed remedy (`bcrypt<4.1`) is still correct and
was verified to fix it.

### L2 (LOW, dbops). `carlos-ctl pma` tore its own panel down when stdin was not a TTY. **Fixed.**

`cmd_pma` passed `-it` unconditionally while `cmd_db` right above it
carefully gates on `isatty`. Run from a script, a non-tty
`ssh host carlos-ctl pma`, or anything piped, podman warned
("the input device is not a TTY") and then tied the container's lifetime to a
stdin already at EOF: the verb published the port, printed the tunnel banner,
and the panel was gone seconds later (observed live — the same invocation
under `setsid` stayed up and served 200). Now uses the same isatty gate as
`db`.

## Live observations worth recording (not defects)

- **The pod specs' db probe fallback shares H1's false-positive**, but
  harmlessly. `_FALLBACK_PROBES["db"]` and the rendered `readinessProbe` are
  `healthcheck.sh --connect || mariadb-admin ping --silent || /dev/tcp:3306`.
  `healthcheck.sh` is present in the mariadb image and does **not**
  false-positive (measured above), so the `mariadb-admin` leg is only reached
  on an image that lacks it; and a false-ready db is absorbed by the carlos
  container's own wait-for-`oscar` loop. Left alone deliberately: changing a
  rendered probe is a wider blast radius than the defect justifies.
- **Rotations still require a full re-play, and the dev path makes that
  visible.** After `rotate db` / `rotate db-root`, the running app kept the
  deploy-time merged properties and logged
  `Access denied for user 'root'@'127.0.0.1'` until `kube play --replace`
  re-ran `carlos-init`. This is the pass-9 note re-confirmed; in production
  `carlos-ctl play` is the restart path, so the flow is correct. The
  Playwright suite is a good detector for it — 7/14 failed against the
  stale-credential app and 14/14 passed after the re-play.
- **`carlos-ctl down` succeeds silently.** It removed the pod and returned 0
  with no output past the target banner. Not wrong, but `status`-style
  confirmation would make a destructive-adjacent verb easier to trust.

## Sandbox caveats

No systemd PID 1, so every systemd-touching leg (unit install in `seal`,
`enable`, `down --disable`, the `status` unit block, the guard/monitor
timers) exercised its **failure** path only — each failed loudly and
specifically, which is the designed behavior, but the success paths remain
covered only by the hermetic suite's stubs. No TPM (`CARLOS_SEAL_NO_TPM=1`
throughout), no WAF/obs pods, no nftables front door, and a local restic
repository (`CARLOS_ACCEPT_LOCAL_REPO=1`). `carlos-ctl play`, `rollback`'s
re-play, and `db-users`' full production layout were reached only up to their
provisioning gates, since the Ansible role cannot complete without systemd.
