# carlos-podman — nineteenth-pass review + live end-to-end test report (2026-08-03)

Scope: a fresh review of `carlos_ctl/`, the Ansible role, the Containerfiles
and the three gate suites, plus a **live end-to-end exercise of the full
production topology** on a clean host: `carlos-ctl setup` → `ansible/site.yml`
against a bare machine → both images built from source with `carlos-ctl build`
→ all three pods started through `carlos-ctl play` → the Ontario Flyway schema
and the DrugRef database loaded through `carlos-ctl db` → `carlos-ctl check` →
the app repo's Playwright login suite through the WAF → every backup tier
including the point-in-time restore drill → a systematic drive of the
**complete** `carlos-ctl` verb matrix. Everything reported fixed through
`REVIEW-2026-08-03-pass18.md` was treated as baseline; only NEW findings are
reported here.

Environment: podman **4.9.3** (the documented floor), Ubuntu 24.04, no systemd
PID 1 (a shim drives the quadlet units), cgroup v1, TLS-intercepting egress
proxy, `nofile` hard cap 4096.

## New findings

### H1 (HIGH): the DrugRef container has no wait-for-db, so one missing/slow database at start kills `/drugref2` permanently — and with it every `carlos-ctl play`

DrugRef's Spring context builds its Hibernate `SessionFactory` **once, at
context start, and never retries**. The pod's `drugref` container ran
`catalina.sh run` directly, so anything that makes the `drugref2` database
unavailable in that one moment is terminal:

- a **fresh install** — the README has you create `drugref2` at step 8, *after*
  the step-6 `play` that starts the pods; and
- **any reboot** where MariaDB is not accepting connections before DrugRef's
  context initializes (both containers start concurrently — `kube play` offers
  no in-pod ordering, which is exactly why the `carlos` container was given a
  wait-for-db loop in finding S14).

Measured live on a from-scratch deploy:

```
2026-08-03 14:23:30 WARN  spi.SqlExceptionHelper - HHH000247: ErrorCode: 1049, SQLState: 42000
2026-08-03 14:23:30 WARN  spi.SqlExceptionHelper - Unknown database 'drugref2'
2026-08-03 14:23:30 ERROR jpa.AbstractEntityManagerFactoryBean - Failed to initialize JPA EntityManagerFactory
03-Aug-2026 14:23:30.797 SEVERE [main] StandardContext.listenerStart Exception sending context initialized event
```

Tomcat stays **up** and serves `404` for `/drugref2/`, `/drugref2/DrugrefService`
and `/` for the rest of the container's life. That is precisely the state the
pod's probes are written to reject (they deliberately refuse 4xx — finding S7),
so `carlos-ctl play`'s readiness gate never greens: it burned the full 1320 s
drugref budget and would have exited 1 with **no `.deployed` marker and no
timers armed** — no backups, no monitoring, no drug-interaction checking, on a
stack whose EMR was otherwise serving fine. A `podman restart` of that one
container (once `drugref2` existed) returned `HTTP/1.1 200` immediately, which
isolates the cause to context-init time rather than the image or the WAR.

**Fix.** Give the drugref container the SAME bounded wait-for-db wrapper the
carlos container carries: poll for the `drugref2` database to be queryable
(credentials read from the assembled `/run/drugref-config/drugref2.properties`,
password off-argv via `MYSQL_PWD`, the same backslash-halving `sed` the carlos
loop needs for a properties-escaped password), up to 600 s, then always `exec
catalina.sh run` — the wait can delay Tomcat, never prevent it. The drugref
image gains `mariadb-client-core` for the same reason the CARLOS image ships it.
Deliberately NOT an initContainer: initContainers must all exit before any app
container starts, so waiting on the db there would deadlock.

This closes the reboot race outright. The fresh-install ordering is a
documentation problem in its own right — see H2.

**Verified live, after the fix.** The drugref image was rebuilt (356 MB ->
374 MB, the +18 MB being the MariaDB client), the playbook re-rendered the pod
spec, the `drugref2` database was DROPPED, and the app pod was recreated:

- with no `drugref2`, the container logged **nothing** — no "Unknown database",
  no `SEVERE ... listenerStart`; `Server startup in` never appeared (catalina
  had not been exec'd), and the probe got **`Connection refused`** on :8180
  rather than the old 404-forever;
- `drugref2` was then created and loaded **while the container waited**, with
  no restart of any kind — and the container **came up by itself within 10 s**,
  serving `HTTP/1.1 200` on `/drugref2/`.

That is the observed failure reversed end to end: the old image needed a manual
`podman restart` at exactly the moment an operator has least context.

### H2 (HIGH, documented-path): the README's Quick start cannot produce a green first `play`

Step 6 runs `carlos-ctl play` and step 6b/8 load the `oscar` and `drugref2`
databases *after* it, "AFTER `play` (the db must be running)". But `play` gates
go-live on the app **and DrugRef** actually serving, and DrugRef provably
cannot (H1) until `drugref2` exists — measured: `play` polled it for its full
1320 s budget. CARLOS itself additionally spends up to 600 s in its own
wait-for-db before deploying against a schema-less `oscar`. So on the documented
path the first `play` ends with "the app is not serving", **writes no go-live
markers and arms no timers** — and nothing in the Quick start tells the operator
that this is expected or that a second `play` is required. An operator who reads the exit
code as a failed install is left with a serving EMR whose backups and
monitoring are silently disarmed (exactly the state the marker/timer gating
exists to make loud).

**Fix.** Say it in the Quick start: the first `play` on a fresh install is the
step that *starts the db so the schema can be loaded*, it is expected to exit
nonzero, and the go-live `play` is the one you run after 6b and 8. The DrugRef
database load is promoted from step 8 to a numbered step before that go-live
play, with the reason (DrugRef never retries its session factory) stated where
the operator is standing.

### M1 (MEDIUM): `rotate <db-root|log-view|obs|age-key|restic>` and `secrets render` silently DROPPED trailing arguments

`cmd_rotate` parsed arguments only for its `db` sub-verb; every other one took
the trailing tokens and discarded them. Each of those is a one-way credential
change on a PHI host:

```
carlos-ctl rotate age-key --dry-run     # re-keyed the sealed-secrets MASTER
carlos-ctl rotate restic --help         # re-passworded the BACKUP REPOSITORY
carlos-ctl rotate db-root --dry-run     # changed the MariaDB root credential
```

`secrets` had the same hole one layer up — the dispatch tested `args[:1] ==
["render"]`, so `carlos-ctl secrets render --dry-run` dropped the flag and
performed the real render of the sealed bundle into the `/run` tmpfs.

This is the identical class the project has already closed three times — the
CLI's `no_arg_verbs` guard, `db-backup`'s one-positional rule ("`db-backup
--help` took a multi-GB plaintext-PHI copy into a directory named `--help`"),
and the `backup <tier>` sub-verb guard — and its own comment states the
principle: *"silently-ignored flags on destructive verbs are how operators get
the opposite of what they asked for."* `rotate` and `secrets` were the two
remaining verbs that still did it.

**Fix.** Refuse trailing arguments on the five argument-less `rotate`
sub-verbs, before any mutation, naming what was dropped and pointing at the one
sub-verb that does take a flag; an unknown sub-verb still gets the usage line
rather than an argument complaint. `secrets` now requires an exact `render`.

### M2 (MEDIUM): `rotate db-root` runs SQL against a db that may still be starting, and blames the stored password when it fails

`rotate db` **restarts the app pod** (it must — the running app keeps
authenticating with the old password). Running the documented next rotation
straight afterwards therefore reaches a db container that `podman ps` lists but
whose mysqld is not yet accepting connections. `_rotate_db_root` only called
`Runner.require_db_running` (a container-NAME check), so the `ALTER USER`
failed and the operator was told:

```
ERROR: ALTER USER failed — is the current CARLOS_DB_ROOT_PASSWORD correct?
```

Measured live: the password was perfectly correct — `carlos-ctl db -e "SELECT
1"` succeeded moments later. The diagnosis sends an operator to hunt a
credential mismatch (and, worse, invites them to "fix" the stored password) for
what is a timing problem. `play`'s own auto-provisioning already had a bounded
"wait until the db actually answers" loop for exactly this reason; the rotation
path did not.

**Fix.** Factor that loop into one shared `dbops.wait_db_accepting()` (so the
two call sites cannot drift), use it in `_rotate_db_root` before the ALTER, and
report the real cause — distinguishing "not accepting connections yet" from an
authentication failure, which the probe returns immediately rather than
retrying until the deadline. Nothing is mutated on the refusal path.

### L1 (LOW): `uninstall` left the obs-store credential in the engine's secret store

The role creates TWO instance-owned podman secrets — `<instance>-db` and
`<instance>-obs-http`, the basic-auth credential fronting the obs stores (180
days of PHI-adjacent logs), which `rotate obs` also recreates. `cmd_uninstall`
removed only the db one. Measured live on the decommission at the end of this
pass: after a clean `uninstall`, `podman secret ls` still showed
`carlos-obs-http`, in a store belonging to the shared service user that
uninstall deliberately preserves. The confirmation banner listed it in neither
the WILL REMOVE nor the WILL PRESERVE half, so nothing told the operator a
credential had outlived the instance.

**Fix.** Remove both, and name both in the banner. Per-instance names, so a
prefix-overlapping sibling's secret is still never touched.

## Environment deviations (what this sandbox could NOT prove)

This host has no systemd as PID 1, so a shim drove the real production control
path — the role's quadlet `.kube` units and root system units/timers — by
translating `systemctl --user -M <user>@ restart <pod>.service` into the
`podman kube play --replace` the quadlet declares, and by executing system
units' `ExecStart`. That exercises `carlos-ctl`'s **primary** (systemd) branch
rather than its documented no-systemd fallback, which is what a production host
runs. Two consequences are visible in the results and are NOT product defects:

1. **The log driver.** With no journald, podman's `journald` driver accepts and
   then discards every line (`podman logs` returns nothing), so the shim starts
   the pods with `k8s-file`. `carlos-ctl check` correctly FAILS on it —
   "`carlos-app-carlos` log driver is 'k8s-file', expected journald" — and the
   three log-stream freshness checks fail for the same reason (nothing reaches
   VictoriaLogs). That is the check doing its job.
2. **Container healthchecks never run.** podman drives them from transient
   systemd timers, so every container sits at `Health: starting` forever. This
   is precisely the degraded shape `_NEVER_RAN_GRACE` exists for, and it worked:
   after 180 s per container `play` fell back to exec'ing the declared probe and
   greened a genuinely-serving stack. It also means every `play` in this report
   costs ~13 minutes of grace it would not cost on a systemd host.

One unexplained anomaly is recorded for honesty rather than reported as a
finding: mid-session the three installed quadlet files under
`/etc/containers/systemd/users/996/` disappeared, which silently moved
`carlos-ctl play` onto its no-systemd fallback. Both plausible suspects were
then tested directly against a live provisioned instance — two full
`tests/run-tests.sh` runs (the second under a 1-second filesystem watcher armed
to dump the process table the instant the files vanished), two full
`tests/ansible-checks.sh` runs (one instrumented to check the directory before
every one of its 37 stages), and a replay of the `seal` -> `rotate age-key` ->
`rotate restic` sequence that bracketed the second occurrence. **None of them
removed the files.** `cmd_uninstall` is the only code in the tree that unlinks
more than the single obs quadlet, and it was never invoked. Re-running the
playbook restored them each time. The visible consequence is worth recording
because it is instructive rather than alarming: with the quadlets gone,
`carlos-ctl play` silently fell back to its no-systemd path and `carlos-ctl
enable` correctly refused with "enable did NOT fully apply — failed: pod-unit
unmask", which is exactly the loud failure that path is written to produce.

## Conclusion

The topology is in good shape: a bare host went to a serving, sealed,
monitored, backed-up CARLOS EMR through the documented tooling, and 77 scripted
verb cases produced zero unexpected exit codes. The three new findings are all
first-install / first-reboot paths — the two HIGH ones cost an operator a
working DrugRef and a green `play` on exactly the run where they have least
context to debug it, and the MEDIUM one hands them a wrong diagnosis during a
credential rotation. All three are fixed here, with regression coverage in the
suite that would have caught each (`tests/ansible-checks.sh` for the pod-spec
wait-for-db and the image's client, `tests/unit` + `tests/run-tests.sh` for the
argument contracts and the readiness probe).
